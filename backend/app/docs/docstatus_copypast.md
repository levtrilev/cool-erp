## Почему для каждой сущности в schemas.py vs мы должны создавать 
DocStatusValue = Literal["draft", "pending", "approved", "active", "archived"] ?

Короткий ответ: общий класс **есть** — это `DocStatus` в `backend/app/core/doctypes/document_base.py`:

```python
class DocStatus:
    """Допустимые значения поля `doc_status` (VARCHAR(32))."""
    DRAFT: str = "draft"
    PENDING: str = "pending"
    APPROVED: str = "approved"
    ACTIVE: str = "active"
    ARCHIVED: str = "archived"
```

Он же используется в `DocumentLifecycleMixin` (`default=DocStatus.DRAFT`, `server_default=text("'draft'")`) и в любом коде, где нужно сравнить/выставить статус. Но дублирование `Literal[...]` по модульным `schemas.py` — не забывчивость, а следствие того, что **`DocStatus` и `DocStatusValue` решают разные задачи и принадлежат разным мирам**. Разберу по слоям.

## 1. Почему `DocStatus` нельзя подставить в аннотацию Pydantic

`DocStatus` — это **пространство имён констант**, а не тип. Его атрибуты аннотированы как `str`, экземпляров этого класса не существует и не должно. Если написать в схеме:

```python
doc_status: DocStatus = DocStatus.DRAFT   # ❌
```

Pydantic воспримет аннотацию как «произвольный класс» и попытается валидировать входящий JSON-стринг проверкой `isinstance(value, DocStatus)` — которая всегда `False`, потому что из JSON прилетает `"draft"`, а не экземпляр класса. Валидация падает, а в OpenAPI попадёт бессмысленная схема объекта вместо перечисления. То есть константный класс пригоден как **источник значений** (для ORM, дефолтов, сравнений в CRUD), но непригоден как **тип поля схемы**.

Pydantic умеет строить закрытое множество строк двумя способами: `Literal[...]` и `Enum`. Поскольку общего `Enum` в ядре нет, каждый модуль объявляет свой `Literal` — это единственный способ получить валидацию и `enum` в OpenAPI, оставаясь в рамках текущей архитектуры.

## 2. Почему `Literal` скопирован по модулям, а не импортирован из ядра

Технически ничто не мешает объявить `DocStatusValue` один раз в `app/core/schemas.py` (или в том же `document_base.py`) и импортировать во все модульные схемы — дублирование на бэкенде исчезнет. Но **на фронтенде единого enum от этого не появится**, и вот почему:

- Pydantic v2 для `Literal` **инлайнит** перечисление в JSON-схему каждой модели, не создавая именованный компонент с `$ref`.
- Orval видит inline-enum у каждого свойства и генерирует отдельный объект на каждое место: `NoteCreateSchemaDocStatus`, `NoteUpdateSchemaDocStatus`, `SalesGoodsCreateSchemaDocStatus`, `SalesItemTypeUpdateSchemaDocStatus`…
- Отсюда вся фронтенд-механика `mapEnumByValue` / `mapStatusForCreate`: формально это разные номинальные типы, хотя значения одни и те же.

То есть общий `Literal` в ядре убрал бы копипасту строк на бэкенде, но не убрал бы главное следствие — размножение enum-типов в сгенерированном клиенте.

## 3. Как выглядело бы настоящее единое źródło истины

Если бы `DocStatus` был объявлен как `str, Enum`:

```python
class DocStatus(str, Enum):
    DRAFT = "draft"
    ...
```

то:

- Pydantic выдал бы в OpenAPI **именованный компонент** (`$ref: DocStatus`), потому что Enum — это полноценный тип с собственной схемой;
- Orval сгенерировал бы **один** общий enum `DocStatus`, используемый всеми Create/Update/Response-схемами всех модулей; фронтенд-маппинги между «create-статусом» и «update-статусом» стали бы не нужны;
- `DocumentLifecycleMixin` продолжил бы работать: `str`-Enum является подклассом `str`, psycopg2 отдаёт в БД лежащую в основе строку `"draft"`, сравнения `doc_status == DocStatus.DRAFT` и `== "draft"` эквивалентны; `server_default=text("'draft'")` и колонка `VARCHAR(32)` не меняются, миграция не нужна;
- Response-схемы можно оставить с `doc_status: str` (чтение из ORM) или перевести на Enum — оба варианта валидны, но для единого enum в Orval лучше Enum.

Почему так не сделано сейчас — вероятно, исторически: константный класс дешевле в сопутствующих рисках (представление `str(member)` в логах, случайное сохранение member вместо value в JSONB-payload'ах событий репликации, сравнения с сырыми строками из БД после `select` без ORM-коэрции). Ни один из этих рисков не критичен, но каждый требует аккуратности при переходе.

## 4. Симметричное дублирование на фронтенде

Та же болезнь в зеркале: карта подписей `DOC_STATUS_LABELS` канонически живёт в `lib/document-form/documentFormHelpers.ts`, но при этом повторно объявлена в `core/notes/schemas.ts`, `modules/sales/orders/schemas.ts` и т.д. Причина та же: модули писались как самодостаточные, а общий слой появился позже и не стал принудительным.

## Итог (вывод для размышления)

Дублирование `DocStatusValue = Literal[...]` существует не потому, что общего класса нет, а потому что общий класс `DocStatus` играет роль **реестра значений для ORM и бизнес-кода**, тогда как схемам нужен **тип-валидатор с представлением в OpenAPI**. Между «класс-константы» и «тип» в текущей архитектуре зазор, который каждый модуль перекрывает своим `Literal`.

Лестница унификации выглядит так:

1. **Статус-кво**: `DocStatus` (значения) + `Literal` в каждом модуле (тип) + N enum'ов в Orval + маппинги на фронте. Работает, но множит сущности.
2. **Полушаг**: один общий `DocStatusValue = Literal[...]` в ядре, импортируемый всеми схемами. Бэкенд-дубликат исчезает; фронтенд-размножение enum'ов остаётся (инлайнинг Literal).
3. **Полный шаг**: `DocStatus(str, Enum)` в ядре. Один тип = одно место = один компонент OpenAPI = один enum в Orval = исчезновение `mapStatusForCreate`-механики для статусов. Цена — внимательный переход str-Enum через ORM, события репликации и логи.

Если когда-нибудь будем делать ревизию документного контракта, вариант 3 окупается тем сильнее, чем больше документных модулей появляется: сейчас каждый новый модуль (goods, item_types, будущие invoices/contracts) платит налог копипастой ещё раз.
