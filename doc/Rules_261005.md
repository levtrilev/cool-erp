# 📋 Полный текст правил проекта Cool ERP (Актуальная версия)

## 🎯 О проекте
Cool ERP — модульный монолит для управления предприятием. Многопользовательская система с multi-tenancy (каждая организация изолирована).

## 🛠 Технологический стек
**Backend**
* FastAPI + Python 3.11+
* SQLAlchemy 2.0 (async, Mapped/mapped_column стиль)
* Pydantic v2 (с `model_config = {"from_attributes": True}`)
* PostgreSQL (схема `public`, UUID через `uuid_generate_v4()`)
* Alembic для миграций

**Frontend**
* React 18 + TypeScript + Vite
* Tailwind CSS + shadcn/ui
* React Hook Form + Zod (валидация)
* TanStack Query (React Query) — управление серверным состоянием
* Orval — автогенерация типобезопасных API-клиентов из OpenAPI
* Lucide React — иконки

## ЧАСТЬ 1. АРХИТЕКТУРА И BACKEND

**Правило №1: Чистая архитектура (ПРИОРИТЕТ)**
При работе со связанными данными всегда использовать:
* SQLAlchemy `relationship` с `back_populates` и `lazy="selectin"` в моделях
* `@property` в ORM-модели для вычисляемых полей (например, `user.tenant_name`)
* `from_attributes=True` в Pydantic-схемах
* Автоматическую конвертацию через `ModelSchema.model_validate(orm_object)`

❌ ЗАПРЕЩЕНО: ручные словари вида `{"id": user.id, "name": user.name, ...}` в роутерах.

**Правило №2: Полный CRUD**
При создании нового CRUD-класса всегда реализовывать полный набор:
* `create`
* `get` (по ID)
* `get_by_*` (по уникальным полям)
* `get_multi` (список с поиском и фильтрами)
* `get_multi_paginated` (возвращает `tuple[list[Model], int]`)
* `update`
* `delete` (с защитой от удаления, если есть связанные записи)

**Правило №3: API версионирование**
* Версия задаётся только через `prefix="/api/v1"` в `main.py`
* Домены не знают о версиях
* При появлении v2: создаётся `router_v2.py` рядом с `router.py`, неизменившиеся роутеры переиспользуются

**Правило №4: Orval-совместимость (Backend)**
* Все эндпоинты, возвращающие списки, используют `PaginatedResponse[Schema]`
* Для обёртки успеха используется `ApiResponse[Schema]` с полями `success`, `message`, `data`
* Явная конвертация ORM → Pydantic через `.model_validate()`

**Правило №5: Именование роутов**
* Публичные эндпоинты: `/public/register`
* Внутренние (для админов): `/register`
* Префиксы роутеров: `/auth`, `/tenants`, `/users`, `/roles` и т.д.

**Правило №6: Именование файлов в доменах**
В каждой папке сущности файлы именуются коротко, БЕЗ префиксов:
* `models.py` — SQLAlchemy модели
* `schemas.py` — Pydantic схемы
* `crud.py` — CRUD-класс с экземпляром `crud_xxx`
* `router.py` — FastAPI роутер
* `services.py` — бизнес-логика (если нужна)
* `dependencies.py` — зависимости (если нужны)

❌ ЗАПРЕЩЕНО: `crud_user.py`, `router_tenant.py` и т.п.

**Правило №7: Именование сущностей во множественном числе**
Все сущности, папки доменов и таблицы в базе данных именуются во множественном числе:
✅ `tenants`, `users`, `roles`, `permissions`, `groups`, `sections`, `doctypes`
❌ `tenant`, `user`, `role`, `permission`, `group`

Это применяется к:
* Названиям папок: `backend/app/core/tenants/`, `frontend/src/core/tenants/`
* Названиям таблиц БД: `public.tenants`, `public.users`
* Названиям переменных в коде: `tenants`, `users` (НЕ `tenant`, `user` для коллекций)

**Правило №30: Паттерн синхронизации подчиненных объектов (Sync Pattern)**
Для всех сущностей, содержащих табличные части (подчиненные объекты), ОБЯЗАТЕЛЬНО использовать паттерн умной синхронизации при сохранении через агрегирующие эндпоинты.

**Примеры:** Роль → Полномочия; Документ → Строки документа.

1. **Базовая схема (`BaseSchema`)** НЕ должна содержать поле `id`. Это "чистый" набор атрибутов.
2. **Схема создания/обновления (`CreateSchema`)** добавляет опциональный `id` для sync-логики:
   ```python
   class PermissionCreateSchema(PermissionBaseSchema):
       id: Optional[uuid.UUID] = None
   ```
3. **Схема ответа (`ResponseSchema`)** добавляет обязательный `id`:
   ```python
   class PermissionResponseSchema(PermissionBaseSchema):
       model_config = ConfigDict(from_attributes=True)
       id: uuid.UUID
   ```
4. **Сервисная логика:** Метод sync загружает существующие объекты из БД и сравнивает с пришедшим списком:
   * Если `id` есть и совпадает → **UPDATE**
   * Если `id` нет → **INSERT**
   * Если в БД есть запись, но её `id` нет во входящем списке → **DELETE**
5. **Атомарность:** Всё выполняется в одной транзакции. Коммит вызывается только в родительском методе после всех операций.
6. **CRUD Update:** Метод `update` принимает полную схему (например, `PermissionCreateSchema`), а не частичную, так как происходит полная перезапись полей.

## ЧАСТЬ 2. FRONTEND — ОБЩИЕ ПРАВИЛА

**Правило №8: Frontend — формы и состояния**
* Для сложных полей в формах использовать `<Controller>` из react-hook-form
* Разделять состояния: `searchInput` (для ввода) и `search` (для запроса) — поиск по кнопке/Enter, а не на каждый символ
* Toast-уведомления через `useToast()` из shadcn/ui

**Правило №9: Использование Orval хуков**
Вместо `useQuery`/`useMutation` напрямую использовать сгенерированные Orval хуки:
```typescript
// ✅ Правильно
const { data, isLoading, refetch } = useReadTenantsTenantsGet({ skip, limit, search });
const deleteMutation = useDeleteTenantTenantsTenantIdDelete();

// ❌ Неправильно
const { data } = useQuery({ queryKey: [...], queryFn: () => readTenantsTenantsGet(...) });
```

**Правило №10: Импорт типов из Orval**
* Функции (API-вызовы) — из `@/api/generated/<domain>/<domain>`
* Типы (схемы) — из `@/api/generated/fastAPI.schemas`

**Правило №21: Именование Pydantic-схем**
Все классы Pydantic-схем (`Base`, `Create`, `Update`, `Response` и т.д.) обязательно должны заканчиваться словом `Schema`.
✅ `SectionBaseSchema`, `SectionCreateSchema`, `SectionResponseSchema`
❌ `SectionBase`, `TenantResponse`

## ЧАСТЬ 3. FRONTEND — СПИСОЧНЫЕ ФОРМЫ (CRUD СТРАНИЦЫ)

**Правило №11: Компактные отступы для десктопа**
* Контейнер: `container mx-auto px-4 py-3`
* Заголовок: `text-xl font-bold`
* Блок заголовка: `flex flex-col md:flex-row justify-between items-start md:items-center gap-2 mb-2`
* Счётчик записей: `<p className="text-xs text-muted-foreground mt-0.5">Всего: {total}</p>`

**Правило №12: Поиск через form**
Поиск должен быть обёрнут в `<form>` для перехвата Enter.

**Правило №13: Таблица с компактным форматированием**
* Обёртка таблицы: `<div className="rounded-md border bg-card">`
* Заголовки таблицы: `className="h-10 py-2"`
* Ячейки данных: `className="py-1"`

**Правило №14: Первая колонка как ссылка для редактирования**
НЕ использовать отдельную кнопку редактирования. Первая колонка должна быть кликабельной ссылкой.

**Правило №15: Пагинация с номерами страниц**
Использовать массив номеров страниц с логикой отображения максимум 5 элементов.

**Правило №16: Кнопка удаления с AlertDialog**
Кнопка удаления должна использовать `AlertDialog` для подтверждения (НЕ `confirm()`).

**Правило №17: Подсветка строки после создания/обновления**
После успешного создания или обновления записи строка в таблице должна подсвечиваться жёлтым цветом на 3 секунды. Автосброс через `useEffect` с `setTimeout(3000)`.

**Правило №18: Умные toast-уведомления с навигацией**
После создания/обновления записи необходимо определить, на какой странице она находится.
ПОРЯДОК ДЕЙСТВИЙ (СТРОГО СОБЛЮДАТЬ):
1. СНАЧАЛА вызвать `refetch()` для обновления данных текущей страницы.
2. ПОТОМ проверить, есть ли запись на текущей странице.
3. Если запись на текущей странице → подсветить строку.
4. Если записи нет на текущей странице → искать в полном списке и показать toast с кнопкой "Перейти".

**Правило №19: Callback-и из модалок в страницу**
Модалки должны принимать callback-и от родительской страницы: `onItemCreated`, `onItemUpdated`.

**Правило №20: Модальные компоненты редактирования**
Все модальные компоненты редактирования ОБЯЗАТЕЛЬНО должны:
* Иметь проверку на null — обёртка `{editingXxx && (...)}`
* Иметь `key` для перемонтирования — `key={editingXxx.id}`

**Правило №22: Обязательная структура состояний списочной страницы**
Каждая списочная CRUD-страница ОБЯЗАТЕЛЬНО должна содержать состояния для поиска (`searchInput`, `search`), пагинации (`page`, `limit`), модалок (`isCreateOpen`, `editModalOpen`, `editingXxx`, `deleteXxxId`) и подсветки (`highlightedXxxId`).

**Правило №23: Алгоритм умной навигации после создания/обновления**
Обработчики ОБЯЗАТЕЛЬНО должны следовать 4-шаговому алгоритму: СНАЧАЛА `await refetch()`, потом проверка. Использовать прямую функцию `readXxx...Get`, а НЕ хук.

**Правило №24: Обязательный вызов `invalidateQueries` в модалке**
Каждая модалка ОБЯЗАТЕЛЬНО должна инвалидировать кэш ДО вызова callback родителя:
`invalidateQueries` → `onOpenChange(false)` → `await onXxxUpdated(...)`.

**Правило №25: Обязательный `refetch()` после удаления**
После успешного удаления записи ОБЯЗАТЕЛЬНО вызывать `await refetch()`.

**Правило №29: Обязательная регулировка ширины колонок во всех таблицах**
Все табличные представления ОБЯЗАТЕЛЬНО должны предоставлять пользователю возможность изменять ширину колонок путём перетаскивания.

1. **Использование хука `useResizableColumns`:** Каждая таблица использует хук из `@/hooks/useResizableColumns`.
2. **Компенсация соседней колонки:** При изменении ширины одной колонки соседняя изменяется на противоположную величину. Общая ширина таблицы не меняется.
3. **Визуальные маркеры:** Каждый заголовок (кроме последнего) содержит полоску-разделитель справа (`cursor-col-resize`).
4. **Кнопка сброса:** Над таблицей есть кнопка "Сбросить ширину", вызывающая `resetWidths()`.
5. **Применение ширин:** Inline-стили `width` на `TableHead` и `TableCell`. Класс `table-fixed` обязателен.
6. **Формат ключа localStorage:** `<domain>-<entity>-table-widths`.
7. **Адаптация содержимого:** Текстовые колонки — `truncate` + `title`; Колонки с элементами — `flex-wrap` + `overflow-hidden`.
8. **Исключения:** Допускается отсутствие регулировки для матриц прав в модалках и таблиц внутри фиксированных модалок.

## ЧАСТЬ 4. БЕЗОПАСНОСТЬ MULTI-TENANCY

**Правило №26: Обязательная фильтрация по tenant_id на уровне Backend (КРИТИЧЕСКИ ВАЖНО)**
Каждый эндпоинт ОБЯЗАТЕЛЬНО должен фильтровать записи по `tenant_id` текущего пользователя. Фронтенд НИКОГДА не решает, какие данные показывать.
* CRUD-методы принимают `current_tenant_id` и `is_superadmin`.
* Роутер извлекает данные из `get_current_session` и передаёт в CRUD.
* При создании/обновлении/удалении проверяется принадлежность записи к тенанту.

**Правило №27: Обязательное использование компонента ReferenceSelect для справочников**
Все выпадающие списки для выбора из справочника ОБЯЗАТЕЛЬНО должны использовать `ReferenceSelect`.

* В формах редактирования обязательно передаётся `selectedLabel`.
*  ЗАПРЕЩЕНО использовать стандартный `<Select>` из shadcn/ui для справочников.

## ЧАСТЬ 6. МОДЕЛИРОВАНИЕ БАЗЫ ДАННЫХ (SQLAlchemy)

**Правило №28: Обязательное указание схемы `public` в моделях SQLAlchemy**
Все модели SQLAlchemy ОБЯЗАТЕЛЬНО должны явно указывать схему базы данных `public` в аргументах таблицы. Это критически важно для корректной работы `relationship`, `ForeignKey` и предотвращения ошибок метаданных ORM в PostgreSQL.

1. **Объявление схемы в `__table_args__`:**
   * Без constraints: `__table_args__ = {"schema": "public"}`
   * С constraints: `__table_args__ = (UniqueConstraint(...), {"schema": "public"})`
2. **Требования к `ForeignKey`:** Все внешние ключи ДОЛЖНЫ включать префикс `public.`:
   ```python
   ForeignKey("public.tenants.id", ondelete="NO ACTION")
   ```
3. **Зачем это нужно:** Предотвращение ошибок ORM (`NoReferencedTableError`), единый стандарт консистентности, безопасность миграций Alembic.
