# 📋 Новое правило проекта

## Правило №30: Паттерн синхронизации подчиненных объектов (Sync Pattern)

Для всех сущностей, содержащих табличные части (подчиненные объекты), **ОБЯЗАТЕЛЬНО** использовать паттерн умной синхронизации при сохранении через агрегирующие эндпоинты.

**Примеры:**
- Роль → Полномочия (permissions)
- Роль → Пользователи (через `user_ids`)
- Документ → Строки документа (line_items)
- Заказ → Позиции заказа
- Складская операция → Движения

---

### 1. Описание паттерна

При сохранении родительской сущности бэкенд выполняет **атомарную синхронизацию** подчиненных объектов в одной транзакции:

1. **Загружает** существующие подчиненные объекты из БД
2. **Сравнивает** с пришедшим списком:
   - Если `id` есть и совпадает с существующим → **UPDATE** (обновляет поля)
   - Если `id` нет → **INSERT** (создаёт новую запись)
   - Если в БД есть запись, но её `id` нет в пришедших данных → **DELETE** (удаляет)
3. **Коммитит** всё в одной транзакции — атомарность гарантирована

---

### 2. Требования к Pydantic-схемам

#### 2.1. Базовая схема (`BaseSchema`)
**НЕ должна содержать поле `id`**. Это "чистый" набор атрибутов объекта.

```python
class PermissionBaseSchema(BaseModel):
    doctype: str
    tenant_id: uuid.UUID
    full_access: bool = False
    # ... остальные поля данных
```

#### 2.2. Схема создания/обновления (`CreateSchema`)
**Добавляет опциональный `id`** для sync-логики:

```python
class PermissionCreateSchema(PermissionBaseSchema):
    # ✅ Опциональный id: если есть — обновляем, если нет — создаём
    id: Optional[uuid.UUID] = None
```

#### 2.3. Схема ответа (`ResponseSchema`)
**Добавляет обязательный `id`**, так как в ответе от БД он всегда присутствует:

```python
class PermissionResponseSchema(PermissionBaseSchema):
    model_config = ConfigDict(from_attributes=True)
    id: uuid.UUID  # ✅ Обязательно
```

---

### 3. Требования к сервисному слою

#### 3.1. Метод sync в сервисе
Каждый сервис, работающий с подчиненными объектами, **ОБЯЗАТЕЛЬНО** должен реализовывать метод синхронизации по следующему шаблону:

```python
async def sync_child_objects(
    self,
    db: AsyncSession,
    parent_id: uuid.UUID,
    incoming_items: list[ChildCreateSchema],
    current_tenant_id: uuid.UUID,
    is_superadmin: bool,
) -> None:
    """
    Умная синхронизация подчиненных объектов.
    UPDATE существующих, INSERT новых, DELETE удалённых.
    """
    # 1. Загружаем существующие объекты
    stmt = select(ChildModel).where(ChildModel.parent_id == parent_id)
    if not is_superadmin:
        stmt = stmt.where(ChildModel.tenant_id == current_tenant_id)
    
    result = await db.execute(stmt)
    existing_items = {item.id: item for item in result.scalars().all()}
    
    # 2. Собираем ID пришедших объектов
    incoming_ids: set[uuid.UUID] = set()
    
    for item_data in incoming_items:
        if item_data.id and item_data.id in existing_items:
            # ✅ UPDATE существующей записи
            await crud_child.update(
                db, item_id=item_data.id, data=item_data,
                current_tenant_id=current_tenant_id, is_superadmin=is_superadmin
            )
            incoming_ids.add(item_data.id)
        else:
            # ✅ INSERT новой записи
            new_item = await crud_child.create(
                db, data=item_data,
                current_tenant_id=current_tenant_id, is_superadmin=is_superadmin
            )
            incoming_ids.add(new_item.id)
    
    # 3. DELETE объектов, которых нет во входящем списке
    items_to_delete = set(existing_items.keys()) - incoming_ids
    for item_id in items_to_delete:
        await crud_child.delete(
            db, item_id=item_id,
            current_tenant_id=current_tenant_id, is_superadmin=is_superadmin
        )
```

#### 3.2. Атомарность
Метод sync **НЕ должен** вызывать `db.commit()` внутри себя. Коммит выполняется в родительском методе (например, `save_role`) после всех операций, чтобы гарантировать атомарность всей транзакции.

#### 3.3. Проверка tenant_id
Каждая операция (UPDATE, INSERT, DELETE) **ОБЯЗАТЕЛЬНО** должна проверять принадлежность объекта к `current_tenant_id` (Правило №26).

---

### 4. Требования к CRUD-слою

#### 4.1. Метод `update`
Метод `update` в CRUD-классе подчиненного объекта **ОБЯЗАТЕЛЬНО** должен принимать схему с полным набором полей (например, `PermissionCreateSchema`), а не частичную схему обновления.

```python
async def update(
    self, 
    db: AsyncSession, 
    item_id: uuid.UUID, 
    data: PermissionCreateSchema,  # ✅ Полный набор полей
    current_tenant_id: uuid.UUID,
    is_superadmin: bool = False
) -> PermissionModel:
    # Исключаем служебные поля из обновления
    update_data = data.model_dump(exclude={'id', 'role_id', 'tenant_id'})
    # ... логика обновления
```

#### 4.2. Метод `delete`
Метод `delete` должен поддерживать массовое удаление по родительскому ID (например, `delete_by_role_id`) для оптимизации, но при sync-паттерне предпочтительно удалять поштучно для точного контроля.

---

### 5. Требования к фронтенду

#### 5.1. Передача `id` для существующих записей
При инициализации состояния подчиненных объектов в модалке редактирования **ОБЯЗАТЕЛЬНО** передавать `id` для существующих записей:

```tsx
const [permissions, setPermissions] = useState<PermissionCreateSchema[]>(
  role?.permissions?.map((p) => ({
    id: p.id,  // ✅ Обязательно для существующих записей
    doctype: p.doctype,
    // ... остальные поля
  })) || []
);
```

#### 5.2. Отсутствие `id` для новых записей
Для новых записей (создаваемых в модалке) поле `id` **НЕ должно передаваться** (или должно быть `undefined`):

```tsx
const newPermission: PermissionCreateSchema = {
  // id не передаём — бэкенд создаст новую запись
  doctype: "invoices",
  tenant_id: currentTenantId,
  full_access: false,
};
```

#### 5.3. Типизация
Тип `PermissionCreateSchema` на фронтенде должен иметь поле `id` как опциональное (`id?: string`), что корректно отражает бизнес-логику.

---

### 6. Требования к агрегирующему эндпоинту

#### 6.1. Единая точка сохранения
Все операции с родительской сущностью и её подчиненными объектами **ОБЯЗАТЕЛЬНО** выполняются через один агрегирующий эндпоинт (например, `POST /roles/save`).

#### 6.2. Порядок операций
Строгий порядок выполнения в сервисе:
1. Создание/обновление родительской сущности
2. Синхронизация подчиненных объектов (sync pattern)
3. Синхронизация связей (например, `user_ids`)
4. `db.commit()` — единый коммит всей транзакции
5. `db.refresh(parent)` — возврат обновлённого объекта

#### 6.3. Обработка ошибок
Если любая из операций (UPDATE, INSERT, DELETE) завершается ошибкой, **вся транзакция откатывается** автоматически благодаря механизму SQLAlchemy.

---

### 7. Пример полной реализации

См. реализацию в `backend/app/core/roles/services.py` → метод `save_role` → блок "УМНАЯ СИНХРОНИЗАЦИЯ полномочий".

Ключевые моменты:
- Загрузка существующих записей: `existing_permissions = {p.id: p for p in result.scalars().all()}`
- Разделение на UPDATE/INSERT по наличию `id`: `if perm_data.id and perm_data.id in existing_permissions`
- Удаление лишних: `perms_to_delete = set(existing_permissions.keys()) - incoming_perm_ids`
- Единый коммит в конце: `await db.commit()`

---

### 8. Исключения

Допускается **НЕ использовать** sync-паттерн в следующих случаях:

1. **Простые связи "один-ко-многим" без редактирования**: если подчиненные объекты создаются один раз и никогда не редактируются (например, логи действий).
2. **Массовые операции**: если подчиненных объектов очень много (тысячи) и sync-паттерн неэффективен — использовать специализированные эндпоинты для массовых операций.
3. **Внешние системы**: если подчиненные объекты синхронизируются из внешних источников (например, справочники из 1С).

---

### 9. Чек-лист для разработчика

При реализации новой сущности с табличной частью:

- [ ] Базовая схема (`BaseSchema`) **НЕ содержит** поле `id`
- [ ] Схема создания (`CreateSchema`) содержит **опциональный** `id`
- [ ] Схема ответа (`ResponseSchema`) содержит **обязательный** `id`
- [ ] В сервисе реализован метод sync по шаблону из п.3.1
- [ ] Метод sync **НЕ вызывает** `db.commit()` внутри себя
- [ ] Каждая операция проверяет `tenant_id` (Правило №26)
- [ ] CRUD-метод `update` принимает полную схему (не частичную)
- [ ] Фронтенд передаёт `id` для существующих записей
- [ ] Фронтенд **НЕ передаёт** `id` для новых записей
- [ ] Агрегирующий эндпоинт выполняет единый `db.commit()` в конце

---

### 10. Обоснование правила

1. **Целостность данных**: Атомарная транзакция гарантирует, что либо все изменения применятся, либо ни одно.
2. **Отсутствие дубликатов**: Sync-паттерн предотвращает накопление дубликатов при повторных сохранениях.
3. **Производительность**: Обновляются только изменённые записи, а не все подряд.
4. **Предсказуемость**: Единый паттерн для всех сущностей упрощает понимание кода.
5. **Безопасность**: Проверка `tenant_id` на каждой операции защищает от утечек данных между тенантами.
