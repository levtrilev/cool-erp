# Правило №3: API версионирование

Все версии API **ОБЯЗАТЕЛЬНО** задаются централизованно через `prefix="/api/v1"` в файле `main.py` при регистрации роутеров. Сами роутеры (домены) **НЕ ДОЛЖНЫ** знать о версии API. При появлении новой версии (v2) создаётся файл `router_v2.py` рядом с существующим `router.py`, а неизменившиеся роутеры переиспользуются.

**СТРОГИЕ ТРЕБОВАНИЯ:**
* Версия API задаётся **ТОЛЬКО** в `main.py` через `prefix="/api/v1"`
* Роутеры доменов **НЕ ДОЛЖНЫ** содержать версию в своём `prefix`
* При появлении новой версии создаётся отдельный файл `router_v2.py`
* Неизменившиеся эндпоинты переиспользуются из старой версии
* **ЗАПРЕЩЕНО** использовать версии в URL эндпоинтов (`/v1/roles`, `/v2/roles`)

---

### 1. Обоснование (Почему это важно)

1. **Централизация управления версиями:** Когда все версии задаются в одном месте (`main.py`), разработчик сразу видит полную картину API. Не нужно открывать каждый роутер, чтобы понять, к какой версии он относится.
2. **Упрощение миграции:** При переходе с v1 на v2 достаточно изменить один префикс в `main.py`, а не редактировать десятки файлов роутеров.
3. **Параллельное сосуществование версий:** Старые клиенты могут продолжать использовать v1, пока новые переходят на v2. Это критически важно для мобильных приложений и внешних интеграций, которые не могут быть обновлены мгновенно.
4. **Чистая архитектура:** Домены (бизнес-логика) не должны знать о транспортных деталях (версиях API). Это соответствует принципу разделения ответственности (SRP).
5. **Orval-совместимость:** Orval генерирует клиенты на основе OpenAPI-спецификации. Централизованное версионирование упрощает конфигурацию генерации и позволяет иметь несколько клиентов для разных версий.
6. **Защита от ошибок:** Единая система версионирования исключает ситуации, когда один разработчик создаёт `/v1/roles`, а другой — `/api/v2/roles`, что приводит к хаосу в URL.

---

### 2. Обязательные требования к реализации

#### 2.1. Централизация версии в `main.py`
Версия API задаётся **ТОЛЬКО** в файле `main.py` при регистрации роутеров:

```python
# ✅ ПРАВИЛЬНО: Версия задаётся в main.py
app.include_router(auth_router, prefix="/api/v1")
app.include_router(roles_router, prefix="/api/v1")
app.include_router(users_router, prefix="/api/v1")
```

#### 2.2. Роутеры без версии
Роутеры доменов **НЕ ДОЛЖНЫ** содержать версию в своём `prefix`:

```python
# ✅ ПРАВИЛЬНО: Роутер не знает о версии
router = APIRouter(prefix="/roles", tags=["Roles"])

# ❌ НЕПРАВИЛЬНО: Роутер знает о версии
router = APIRouter(prefix="/api/v1/roles", tags=["Roles"])
router = APIRouter(prefix="/v1/roles", tags=["Roles"])
```

#### 2.3. Создание новой версии (v2)
При появлении новой версии API:
1. Создаётся файл `router_v2.py` рядом с существующим `router.py`
2. В `router_v2.py` реализуются **только изменённые** эндпоинты
3. Неизменившиеся эндпоинты переиспользуются из старого роутера
4. В `main.py` регистрируются оба роутера (v1 и v2)

#### 2.4. Поддержка нескольких версий
Старая версия API **ОБЯЗАТЕЛЬНО** должна продолжать работать, пока существуют клиенты, использующие её. Удаление версии допускается только после полного прекращения её использования.

### 3. Примеры кода

#### ✅ ПРАВИЛЬНО: Структура с одной версией (v1)

**Файл `backend/app/main.py`:**
```python
from fastapi import FastAPI
from app.core.auth.router import router as auth_router
from app.core.roles.router import router as roles_router
from app.core.users.router import router as users_router

app = FastAPI(title="Cool ERP", version="1.0.0")

# ✅ Версия задаётся ТОЛЬКО здесь
app.include_router(auth_router, prefix="/api/v1")
app.include_router(roles_router, prefix="/api/v1")
app.include_router(users_router, prefix="/api/v1")
```

**Файл `backend/app/core/roles/router.py`:**
```python
from fastapi import APIRouter

# ✅ Роутер НЕ знает о версии
router = APIRouter(prefix="/roles", tags=["Roles"])

@router.get("/")
async def get_roles():
    # Логика получения списка ролей
    pass

@router.post("/save")
async def save_role():
    # Логика сохранения роли
    pass
```

**Итоговая карта URL:**
```
GET  /api/v1/roles/       ← Версия задана в main.py
POST /api/v1/roles/save   ← Версия задана в main.py
```

#### ✅ ПРАВИЛЬНО: Структура с двумя версиями (v1 и v2)

Предположим, в v2 мы изменили эндпоинт получения списка ролей (добавили новую фильтрацию), но эндпоинт сохранения остался прежним.

**Файл `backend/app/core/roles/router.py` (v1 — остаётся без изменений):**
```python
from fastapi import APIRouter

router = APIRouter(prefix="/roles", tags=["Roles v1"])

@router.get("/")
async def get_roles_v1():
    # Старая логика без новой фильтрации
    pass

@router.post("/save")
async def save_role():
    # Логика сохранения (не изменилась)
    pass
```

**Файл `backend/app/core/roles/router_v2.py` (v2 — только изменённые эндпоинты):**
```python
from fastapi import APIRouter
from app.core.roles.router import router as v1_router  # ✅ Переиспользуем v1

router_v2 = APIRouter(prefix="/roles", tags=["Roles v2"])

# ✅ Переиспользуем неизменившийся эндпоинт из v1
router_v2.post("/save")(v1_router.routes[-1].endpoint)

# ✅ Новый эндпоинт с изменённой логикой
@router_v2.get("/")
async def get_roles_v2(
    skip: int = 0,
    limit: int = 10,
    search: str | None = None,
    is_active: bool | None = None,  # ✅ Новый параметр фильтрации
):
    # Новая логика с поддержкой is_active
    pass
```

**Файл `backend/app/main.py`:**
```python
from fastapi import FastAPI
from app.core.roles.router import router as roles_router_v1
from app.core.roles.router_v2 import router_v2 as roles_router_v2

app = FastAPI(title="Cool ERP", version="2.0.0")

# ✅ Обе версии зарегистрированы параллельно
app.include_router(roles_router_v1, prefix="/api/v1")
app.include_router(roles_router_v2, prefix="/api/v2")
```

**Итоговая карта URL:**
```
GET  /api/v1/roles/       ← Старая версия (без is_active)
POST /api/v1/roles/save   ← Старая версия (сохранение)

GET  /api/v2/roles/       ← Новая версия (с is_active)
POST /api/v2/roles/save   ← Переиспользуется из v1
```

#### ❌ НЕПРАВИЛЬНО: Версия внутри роутера

```python
# ❌ ГРУБОЕ НАРУШЕНИЕ ПРАВИЛА №3
# Файл backend/app/core/roles/router.py
router = APIRouter(prefix="/api/v1/roles", tags=["Roles"])  # ❌ Роутер знает о версии

@router.get("/")
async def get_roles():
    pass
```
*Почему это плохо:*
1. При переходе на v2 придётся менять все роутеры.
2. Версия "размазана" по коду — не видно полной картины API.
3. Невозможно легко переиспользовать роутер для другой версии.

#### ❌ НЕПРАВИЛЬНО: Версия в URL эндпоинтов

```python
# ❌ ГРУБОЕ НАРУШЕНИЕ ПРАВИЛА №3
router = APIRouter(prefix="/roles", tags=["Roles"])

@router.get("/v1/")  # ❌ Версия в URL эндпоинта
async def get_roles_v1():
    pass

@router.get("/v2/")  # ❌ Версия в URL эндпоинта
async def get_roles_v2():
    pass
```
*Почему это плохо:*
1. Нарушает REST-стандарты — версия должна быть в префиксе, а не в ресурсе.
2. URL `/roles/v1/` семантически неверен — `v1` не является частью ресурса `roles`.
3. Orval не сможет корректно сгенерировать клиенты.

#### ❌ НЕПРАВИЛЬНО: Удаление старой версии без предупреждения

```python
# ❌ ОШИБКА: Удалили v1, сломав старых клиентов
app.include_router(roles_router_v2, prefix="/api/v2")
# ❌ app.include_router(roles_router_v1, prefix="/api/v1")  # Удалено!
```
*Почему это плохо:* Мобильные приложения и внешние интеграции, использующие v1, перестанут работать. Это критическая ошибка для production-систем.

#### ❌ НЕПРАВИЛЬНО: Дублирование неизменившихся эндпоинтов

```python
# ❌ ОШИБКА: Дублирование кода
# router_v2.py
@router_v2.post("/save")
async def save_role_v2():
    # ❌ Точно такая же логика, как в v1
    pass
```
*Почему это плохо:* Нарушает принцип DRY. При изменении логики сохранения придётся править в двух местах.

### 4. Нюансы и лучшие практики

#### 4.1. Стратегии версионирования
Существует три основных подхода к версионированию API:

**1. URL Path Versioning (используется в Cool ERP):**
```
GET /api/v1/roles
GET /api/v2/roles
```
✅ **Преимущества:** Простота, явность, легко кэшировать
❌ **Недостатки:** "Грязные" URL

**2. Header Versioning:**
```
GET /api/roles
Header: API-Version: 1
```
✅ **Преимущества:** Чистые URL
❌ **Недостатки:** Сложнее тестировать, не видно версию в логах

**3. Query Parameter Versioning:**
```
GET /api/roles?version=1
```
✅ **Преимущества:** Гибкость
❌ **Недостатки:** Может конфликтовать с другими параметрами

**Cool ERP использует URL Path Versioning**, так как это наиболее предсказуемый и легко отлаживаемый подход.

#### 4.2. Когда создавать новую версию
Новая версия API **ОБЯЗАТЕЛЬНО** создаётся при:
* Изменении структуры ответа (удаление/переименование полей)
* Изменении обязательных параметров запроса
* Изменении бизнес-логики, ломающей обратную совместимость
* Изменении формата данных (например, `date` → `datetime`)

Новая версия **НЕ требуется** при:
* Добавлении новых опциональных полей в ответ
* Добавлении новых опциональных параметров запроса
* Исправлении багов (если поведение не меняется)
* Изменении внутренней реализации без изменения контракта

#### 4.3. Переиспользование эндпоинтов
При создании v2 **ОБЯЗАТЕЛЬНО** переиспользовать неизменившиеся эндпоинты из v1:

```python
# router_v2.py
from app.core.roles.router import router as v1_router

router_v2 = APIRouter(prefix="/roles", tags=["Roles v2"])

# ✅ Переиспользуем эндпоинт из v1
router_v2.add_api_route(
    "/save",
    v1_router.routes[-1].endpoint,  # Получаем функцию-обработчик
    methods=["POST"],
)
```

Альтернативный способ — вынести общую логику в сервис:

```python
# services.py
class RoleService:
    async def save_role(self, db, data):
        # Общая логика сохранения
        pass

# router.py (v1)
@router.post("/save")
async def save_role_v1(data: RoleSaveSchema):
    return await role_service.save_role(db, data)

# router_v2.py
@router_v2.post("/save")
async def save_role_v2(data: RoleSaveSchema):
    # ✅ Переиспользуем сервис
    return await role_service.save_role(db, data)
```

#### 4.4. Документация версий
Swagger UI **ОБЯЗАТЕЛЬНО** должен отображать все версии API. Используйте `tags` для группировки:

```python
router_v1 = APIRouter(prefix="/roles", tags=["Roles v1"])
router_v2 = APIRouter(prefix="/roles", tags=["Roles v2"])
```

В Swagger UI это будет выглядеть как:
```
Roles v1
  GET /api/v1/roles
  POST /api/v1/roles/save

Roles v2
  GET /api/v2/roles
  POST /api/v2/roles/save
```

#### 4.5. OpenAPI-спецификация
Для каждой версии API **ОБЯЗАТЕЛЬНО** генерировать отдельную OpenAPI-спецификацию:

```python
# main.py
from fastapi.openapi.utils import get_openapi

# OpenAPI для v1
openapi_v1 = get_openapi(
    title="Cool ERP API v1",
    version="1.0.0",
    routes=[route for route in app.routes if "/v1/" in route.path],
)

# OpenAPI для v2
openapi_v2 = get_openapi(
    title="Cool ERP API v2",
    version="2.0.0",
    routes=[route for route in app.routes if "/v2/" in route.path],
)

@app.get("/openapi/v1.json", include_in_schema=False)
async def get_openapi_v1():
    return openapi_v1

@app.get("/openapi/v2.json", include_in_schema=False)
async def get_openapi_v2():
    return openapi_v2
```

#### 4.6. Orval-конфигурация
Orval должен генерировать клиенты для каждой версии отдельно:

```typescript
// orval.config.ts
export default {
  v1: {
    input: "http://localhost:8000/openapi/v1.json",
    output: {
      target: "./src/api/generated/v1",
      client: "react-query",
    },
  },
  v2: {
    input: "http://localhost:8000/openapi/v2.json",
    output: {
      target: "./src/api/generated/v2",
      client: "react-query",
    },
  },
};
```

#### 4.7. Миграция клиентов
При переходе на новую версию **ОБЯЗАТЕЛЬНО**:
1. Опубликовать changelog с описанием изменений
2. Предупредить всех потребителей API (фронтенд, мобильные приложения, внешние интеграции)
3. Установить дедлайн миграции (обычно 3-6 месяцев)
4. После дедлайна — отключить старую версию с предупреждением

#### 4.8. Связь с Правилом №5 (Именование роутов)
Правило №3 работает в паре с Правилом №5:
* **Правило №5** задаёт префиксы доменов (`/roles`, `/users`)
* **Правило №3** добавляет версию (`/api/v1`)

```python
# ✅ ПРАВИЛЬНО: Версия + домен
app.include_router(roles_router, prefix="/api/v1")  # /api/v1/roles

# ❌ НЕПРАВИЛЬНО: Домен + версия
router = APIRouter(prefix="/roles/v1")  # ❌ /roles/v1 — неверно
```

#### 4.9. Связь с Правилом №4 (Orval-совместимость)
Orval автоматически распознаёт версии API, если они правильно описаны в OpenAPI-спецификации. Это позволяет генерировать отдельные клиенты для v1 и v2.

#### 4.10. Связь с Правилом №6 (Именование файлов)
Файлы роутеров для разных версий именуются с суффиксом версии:
```text
backend/app/core/roles/
 ├── router.py        # ✅ v1 (основная версия)
 ├── router_v2.py     # ✅ v2 (новая версия)
 └── router_v3.py     # ✅ v3 (если появится)
```

### 5. Типичные ошибки и их исправление

| Ошибка | Исправление |
| :--- | :--- |
| `prefix="/api/v1/roles"` в роутере | `prefix="/roles"` + версия в `main.py` |
| `@router.get("/v1/")` в эндпоинте | Версия только в префиксе `main.py` |
| Удаление v1 без предупреждения | Поддержка v1 и v2 параллельно |
| Дублирование неизменившихся эндпоинтов | Переиспользование через `add_api_route` или сервис |
| Отсутствие документации для v2 | Генерация отдельной OpenAPI-спецификации |
| Orval генерирует один клиент для всех версий | Настройка отдельных `input` для каждой версии |

### 6. Чек-лист для разработчика

При создании или изменении API проверьте:

**Структура версионирования:**
- [ ] Версия API задаётся в `main.py` через `prefix="/api/v1"`?
- [ ] Роутеры доменов НЕ содержат версию в своём `prefix`?
- [ ] Все роутеры зарегистрированы в `main.py` с правильным префиксом?

**Создание новой версии (v2):**
- [ ] Создан ли файл `router_v2.py` рядом с `router.py`?
- [ ] Переиспользуются ли неизменившиеся эндпоинты из v1?
- [ ] Реализованы ли только изменённые эндпоинты в v2?
- [ ] Зарегистрирован ли `router_v2` в `main.py` с `prefix="/api/v2"`?

**Документация:**
- [ ] Используются ли `tags` для группировки версий в Swagger?
- [ ] Генерируется ли отдельная OpenAPI-спецификация для каждой версии?
- [ ] Опубликован ли changelog с описанием изменений?

**Orval-совместимость:**
- [ ] Настроен ли Orval для генерации клиентов для каждой версии?
- [ ] Корректно ли работают хуки на фронтенде для разных версий?

**Миграция:**
- [ ] Предупреждены ли все потребители API о переходе на новую версию?
- [ ] Установлен ли дедлайн миграции?
- [ ] Сохраняется ли обратная совместимость v1?

**Безопасность:**
- [ ] Применяется ли middleware аутентификации ко всем версиям API?
- [ ] Не забыты ли проверки `tenant_id` в новых эндпоинтах v2?

### 7. Таблица соответствий

| Ситуация | Действие |
| :--- | :--- |
| Добавление опционального поля в ответ | Не создавать новую версию |
| Удаление обязательного поля из ответа | Создать v2 |
| Изменение формата даты (`date` → `datetime`) | Создать v2 |
| Добавление нового опционального параметра | Не создавать новую версию |
| Изменение обязательного параметра | Создать v2 |
| Исправление бага без изменения контракта | Не создавать новую версию |
| Изменение бизнес-логики, ломающее совместимость | Создать v2 |

---

Следование этому правилу гарантирует, что API Cool ERP будет:
✅ **Централизованным** — все версии управляются из одного места
✅ **Масштабируемым** — добавление новых версий не требует изменения существующих роутеров
✅ **Обратно совместимым** — старые клиенты продолжают работать
