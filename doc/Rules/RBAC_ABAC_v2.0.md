## 1. Термины и определения

| Термин | Определение |
|--------|-------------|
| Организация (Тенант) | Изолированное пространство данных. Каждая запись принадлежит ровно одной Организации. |
| Пользователь | Учётная запись, принадлежащая одной Организации. Имеет одно или несколько Назначений Ролей. |
| Администратор | Пользователь с `is_admin = true` в своей Организации. |
| Суперадмин | Пользователь с `is_superadmin = true`. Видит все Организации. Не освобождается от правил тег-фильтрации. |
| Роль | Именованный набор: Разделы × Типы документов × Уровни доступа. |
| Назначение роли (Grant) | Связь «Пользователь ↔ Роль» с необязательными сроками действия. |
| Раздел | Логическое пространство доступа. Не является физической структурой хранения. Задаётся полем `section_id` в записи документа. |
| Тип документа (doctype) | Строковый код категории документа (`"invoices"`, `"contracts"`). Несёт глобальные переключатели тег-применимости. |
| Документ | Экземпляр данных. Обязан соблюдать контракт атрибутов доступа (§3.3). |
| Тег | Строка `<пространство>:<значение>` (`регион:сибирь`). |
| Уровень доступа | полный (4) > редактор (3) > автор (2) > читатель (1) > нет (0). |
| Полный уровень | Уровень 4. Включает право вручную управлять тегами документа. |
| Область доступа | Совокупность записей, видимых пользователю. Формируется пересечением слоёв: Тенант × Разделы × Типы × Теги, с определением уровня. |
| Делегирование | Временная передача конкретных прав на конкретные документы от Делегатора Делегату. |
| Аудит | Неизменяемая регистрация фактов изменения настроек доступа и (минимально) фактов изменения данных. |

## 2. Общие принципы

| Принцип | Формулировка |
|---------|--------------|
| 2.1 Явное управление | Право возникает только из явно заданных настроек: Разделы в роли, записи Permissions, теги пользователя, теги документа, переключатели Типа документа. Пустое значение никогда не означает «всё». |
| 2.2 Безопасность по умолчанию | При отсутствии любых из необходимых настроек — доступа нет. Ошибка конфигурации приводит к отсутствию доступа, а не к его появлению. |
| 2.3 Видимость ≠ уровень | Разделы и Теги отвечают на вопрос «существует ли запись для пользователя». Уровни отвечают на вопрос «что можно делать с записью». **Если право на чтение отсутствует — запись не существует для пользователя: не возвращается в списке, не находится поиском.** |
| 2.4 Приоритет запрета видимости | Если запись не прошла проверку видимости (Раздел или Теги) — уровень доступа не вычисляется и не применяется, в том числе для Полного уровня, Администраторов и Суперадмина. |
| 2.5 Отсутствие автоматических исключений | Администратор и Суперадмин не получают доступ автоматически. Для доступа они включаются в соответствующую Роль (и, при необходимости, наделяются тегами). |
| 2.6 RLS-семантика | Скрытые записи не возвращаются в списках, не находятся поиском, не участвуют в агрегатах и выгрузках. Пользователь не получает информации об их существовании. |
| 2.7 Аудируемость | Каждое изменение настроек доступа регистрируется в неизменяемом журнале (§12.1). |

## 3. Слои разграничения доступа

```
Слой 1: Тенант                    — жёсткая изоляция данных (исключение — раздел «Общий», §4.3)
   ↓
Слой 2: Раздел                    — ВИДИМОСТЬ (явно в роли)
   ↓
Слой 3: Тип документа             — наличие записи Permissions в роли
   ↓
Слой 4: Теги                      — ВИДИМОСТЬ (глобально для Типа документа)
   ↓
Слой 5: Уровень доступа           — ЧТО МОЖНО ДЕЛАТЬ (максимум из ролей)
```

### 3.1. Слой 1 — Тенант

| Правило | Формулировка |
|---------|--------------|
| 3.1.1 | Документ принадлежит ровно одной Организации (`tenant_id`). |
| 3.1.2 | Пользователь видит документы только своей Организации. |
| 3.1.2.1 | **Исключение (новое в 2.1):** документ, находящийся в Разделе типа «Общий» (платформенный), видим пользователям любой Организации при соблюдении слоёв «Раздел», «Тип документа», «Теги» (§4.3). Тенантная изоляция таких документов ослабляется до кросс-организационной видимости. |
| 3.1.3 | Суперадмин видит документы всех Организаций (в границах своих Ролей, Разделов и Тегов). |
| 3.1.4 | Фильтрация выполняется на уровне SQL, а не в памяти приложения. |

### 3.2. Слой 2 — Раздел

| Правило | Формулировка |
|---------|--------------|
| 3.2.1 | Раздел — логический механизм доступа, не связан с физическим хранением. |
| 3.2.2 | Документ содержит `section_id` — обязательное поле. |
| 3.2.3 | Роль содержит `section_ids` — явный список разделов. |
| 3.2.4 | Если `section_ids` роли пуст или `NULL` — роль не даёт доступа ни к одному документу (Принцип 2.1). |
| 3.2.5 | Если `section_ids` непуст — документ доступен через роль только при `document.section_id ∈ role.section_ids`. |

### 3.3. Контракт атрибутов доступа

Любое хранилище документов обязано содержать атрибуты:

| Атрибут | Тип | Обязательность | Назначение |
|---------|-----|----------------|------------|
| `tenant_id` | UUID | Да | Слой 1 |
| `section_id` | UUID | Да | Слой 2 |
| `author_id` | UUID | Да | Уровень «автор» |
| `or_tags` | ARRAY(VARCHAR) | Да (допускается `NULL`) | Слой 4, ИЛИ |
| `and_tags` | ARRAY(VARCHAR) | Да (допускается `NULL`) | Слой 4, И |

### 3.4. Слой 3 — Тип документа

| Правило | Формулировка |
|---------|--------------|
| 3.4.1 | Для Типа документа в роли существует запись `Permission` с набором уровней. |
| 3.4.2 | Если ни одна активная роль не имеет записи `Permission` для `document.doctype` — доступа нет. |
| 3.4.3 | Допустимые для роли Типы документов фильтруются по Организации роли через M2M `doctype_tenants`. |

### 3.5. Слой 4 — Теги

См. §6. Переключатели применимости — на уровне Типа документа (§7).

### 3.6. Слой 5 — Уровень доступа

См. §5.

## 4. Разделы

### 4.1. Типы Разделов

| Тип | Область | Создание | Удаление | Формат имени |
|-----|---------|----------|----------|--------------|
| Общий (платформенный) | Все Организации | При инициализации платформы | Запрещено | `Общий` |
| Общий для организации | Одна Организация | Автоматически при создании Организации | Запрещено | `Общий-<Организация>` (новое в 2.1) |
| Произвольный | Одна Организация | Администратор Организации | Администратор, при отсутствии документов | Задаётся Администратором |

### 4.2. Явное требование

| Правило | Формулировка |
|---------|--------------|
| 4.2.1 | Роль без явно заданных `section_ids` является недействующей: она не добавляет пользователю никаких прав. |
| 4.2.2 | Интерфейс редактирования Роли обязан отображать предупреждение: «Роль не даёт прав: не заданы Разделы» при пустом `section_ids`. |
| 4.2.3 | Сохранение роли без Разделов разрешено (роль может быть заготовкой), но такая роль не участвует в вычислении доступа. |
| 4.2.4 | Для доступа к общедоступному контенту роль должна явно включать Раздел «Общий» и/или «Общий-<Организация>». |

### 4.3. Раздел «Общий» (платформенный) — кросс-организационный доступ (новое в 2.1)

| Правило | Формулировка |
|---------|--------------|
| 4.3.1 | Раздел типа «Общий» (платформенный) предоставляет кросс-организационную видимость: документ в этом разделе видим пользователям любой Организации при соблюдении слоёв «Раздел», «Тип документа», «Теги». |
| 4.3.2 | Доступ к документам раздела «Общий» предоставляется только через явное включение этого раздела в роль (§4.2.4). Автоматического доступа нет (§2.1, §2.5). |
| 4.3.3 | Для всех пользователей, кроме Суперадмина, документы раздела «Общий» доступны **только для чтения**: итоговый уровень понижается до 1 (читатель), `can_delete = false`. |
| 4.3.4 | Понижение уровня до чтения применяется **в том числе к Автору и Редактору**: в разделе «Общий» Автор и Редактор теряют право изменения и удаления. |
| 4.3.5 | Суперадмин может изменять и удалять документы раздела «Общий», но только если он прошёл общие слои доступа (роли, разделы, Permission, теги). Автоматического исключения нет (§2.5). |
| 4.3.6 | Создание документа в разделе «Общий» и перемещение документа в раздел «Общий» доступны только Суперадмину. |
| 4.3.7 | Понижение уровня (§4.3.3) выполняется **после** вычисления видимости: документ без тегов с ролевым уровнем 4 остаётся видимым всем пользователям с ролью на «Общий», но только для чтения (если они не Суперадмины). |

### 4.4. Раздел «Общий-<Организация>»

| Правило | Формулировка |
|---------|--------------|
| 4.4.1 | Раздел «Общий-<Организация>» создаётся автоматически при создании Организации и защищён от удаления, переименования и изменения. |
| 4.4.2 | Раздел «Общий-<Организация>» не даёт кросс-организационного доступа: это обычный раздел, ограниченный своей Организацией. Кросс-организационную видимость даёт только раздел «Общий» (платформенный). |
| 4.4.3 | Функциональное назначение раздела — «раздел по умолчанию» для первоначальной настройки ролей Организации. |

## 5. Уровни доступа

### 5.1. Иерархия (исправлено в 2.1)

```
4 (полный) > 3 (редактор) > 2 (автор) > 1 (читатель) > 0 (нет доступа)
```

| Уровень | Флаг | Права |
|---------|------|-------|
| Полный (4) | `full_access` | Просмотр, создание, изменение любых записей, удаление, ручное управление тегами доступа документа |
| Редактор (3) | `editor` | Просмотр + изменение + удаление **любых** документов типа (любого автора) |
| Автор (2) | `author` | Просмотр + изменение + удаление **только своих** документов (где `author_id = user.id`) |
| Читатель (1) | `reader` | Только просмотр |
| Нет (0) | — | Запись не существует для пользователя |

**Важное семантическое уточнение (новое в 2.1):** уровень «Автор» НЕ является более высоким, чем «Редактор». Наоборот: Редактор имеет более широкие полномочия, так как может изменять и удалять документы любого автора, тогда как Автор — только свои. Числовая иерархия (3 > 2) отражает именно **широту полномочий**.

**Следствие для вычисления максимума:** если пользователь имеет флаги `editor` и `author` одновременно, и при этом является автором документа, итоговый уровень = 3 (редактор), а не 2. Проверка флага `editor` выполняется до проверки `author`.

### 5.2. Право на удаление

| Правило | Формулировка |
|---------|--------------|
| 5.2.1 | `can_delete` — независимый флаг, не входит в иерархию уровней. |
| 5.2.2 | Может быть установлен при любом уровне, включая «читатель». |
| 5.2.3 | Итог по пользователю — логическое ИЛИ по всем прошедшим роли. |
| 5.2.4 | **Новое в 2.1:** `can_delete` дополнительно устанавливается автоматически, если итоговый уровень доступа ≥ 2 (редактор или автор). Итоговая формула: `can_delete = (флаг из любой прошедшей роли) OR (итоговый уровень ≥ 2)`. |
| 5.2.5 | **Новое в 2.1:** для не-Суперадмина в разделе «Общий» `can_delete` всегда `false` (§4.3.3). |

**Пояснение к 5.2.4:** уровень «автор» (2) присваивается только для собственных документов пользователя, поэтому автоматическое право удаления при уровне ≥ 2 корректно: автор удаляет только свои документы, редактор — любые.

### 5.3. Разрешение конфликтов между ролями

| Правило | Формулировка |
|---------|--------------|
| 5.3.1 | Роли задают «что разрешено». |
| 5.3.2 | При нескольких уровнях для одного Типа документа применяется максимальный уровень. |
| 5.3.3 | `can_delete` объединяется по ИЛИ. |
| 5.3.4 | Конфликты видимости (Разделы, Теги) разрешаются не максимумом, а правилом «прошла хотя бы одна роль по разделам И пройдена глобальная тег-проверка» (§8). |

### 5.4. Режим «только чтение» при недостаточном уровне (новое в 2.1)

| Правило | Формулировка |
|---------|--------------|
| 5.4.1 | Если у пользователя есть право на чтение (уровень ≥ 1), но недостаточный уровень для изменения, интерфейс открывает документ в режиме «только чтение». |
| 5.4.2 | В режиме «только чтение» все значения полей документа отображаются, но недоступны для изменения. Кнопка сохранения не отображается. |
| 5.4.3 | Режим «только чтение» применяется также при пессимистической блокировке документа другим пользователем (423). |

## 6. Теги доступа (ABAC)

*(Раздел наследует версию 2.0 без изменений. Приведены ключевые правила.)*

### 6.1–6.4

См. версию 2.0. Без изменений: назначение тегов, формат `<пространство>:<значение>`, теги пользователя (`UserModel.tags`), теги документа (`or_tags`, `and_tags`).

### 6.5. Два поля тегов документа

- **6.5.1** `or_tags` — фильтр по совпадению (ИЛИ): пользователь должен иметь хотя бы один тег из `doc.or_tags`.
- **6.5.2** `and_tags` — обязательный допуск (И): пользователь должен иметь все теги из `doc.and_tags`.

### 6.6. Правило «нет тегов при включённом применении»

| Правило | Формулировка |
|---------|--------------|
| 6.6.1 | Если включено применение `or_tags` и `doc.or_tags` пуст/`NULL` — документ виден только пользователям с уровнем 4. |
| 6.6.2 | Если включено применение `and_tags` и `doc.and_tags` пуст/`NULL` — документ виден только пользователям с уровнем 4. |
| 6.6.3 | Достаточно срабатывания любого из условий 6.6.1/6.6.2. |
| 6.6.4 | Администраторы и Суперадминистраторы не освобождаются. |
| 6.6.5 | Для пользователей с уровнем 4 тег-проверка по пустым полям не выполняется. |

### 6.7. Проверка тегов для заполненных значений

```
ФУНКЦИЯ check_tags(user_tags, doc_or_tags, doc_and_tags, or_enforced, and_enforced):
  ШАГ 1: and_tags (обязательный допуск)
  ЕСЛИ and_enforced И doc_and_tags НЕ ПУСТ:
      ЕСЛИ НЕ (doc_and_tags ⊆ user_tags): → ОТКАЗ
  ШАГ 2: or_tags (белый список)
  ЕСЛИ or_enforced И doc_or_tags НЕ ПУСТ:
      ЕСЛИ user_tags ∩ doc_or_tags = ∅: → ОТКАЗ
  → ТЕГ-ПРОВЕРКА ПРОЙДЕНА
```

### 6.8. Действие тегов — для всех без исключений

Без изменений (включая единственное исключение — активное Делегирование, §11).

## 8. Полный алгоритм вычисления доступа

### 8.1. Формальное описание

```
ВХОД:
  user      — пользователь: tenant_id, is_superadmin, tags, активные Назначения Ролей
  document  — документ: tenant_id, doctype, section_id, section_type, author_id, or_tags, and_tags
  now       — текущее время (UTC)

ВЫХОД:
  visible    : bool          — существует ли запись для пользователя
  level      : 0..4          — итоговый уровень доступа
  can_delete : bool          — право на удаление
  source     : ROLE | DELEGATION
```

### 8.2. Псевдокод (обновлён в 2.1)

```
FUNCTION resolve_access(user, document, now) -> (visible, level, can_delete, source):

   ── ШАГ 1. ТЕНАНТ + ИСКЛЮЧЕНИЕ ПЛАТФОРМЕННОГО РАЗДЕЛА ────────
   is_platform = (document.section_type = 'platform')
   IF document.tenant_id ≠ user.tenant_id
      AND user.is_superadmin = false
      AND is_platform = false:                          // §3.1.2.1
          RETURN (false, 0, false, NONE)

   ── ШАГ 2. ДЕЙСТВУЮЩИЕ НАЗНАЧЕНИЯ РОЛЕЙ ──────────────────────
   grants = SELECT g FROM user_role_grants g
            WHERE g.user_id = user.id
              AND (g.valid_from  IS NULL OR g.valid_from  ≤ now)
              AND (g.valid_until IS NULL OR g.valid_until >  now)
   IF grants = ∅:
       roles = []                      // обратная совместимость: user.role_ids
   ELSE:
       roles = load_roles(grants.role_ids)

   ── ШАГ 3. КАНДИДАТЫ-РОЛИ: ЯВНЫЕ РАЗДЕЛЫ + PERMISSION ─────────
   cands = []
   FOR role IN roles:
       IF role.section_ids IS NULL OR role.section_ids = ∅:
           CONTINUE                                   // Правило 4.2.1
       IF document.section_id ∉ role.section_ids:
           CONTINUE                                   // Правило 3.2.5
       perm = role.permissions.find(doctype = document.doctype)
       IF perm IS NULL:
           CONTINUE                                   // Правило 3.4.2
       cands.append((role, perm))

   ── ШАГ 4. МАКСИМАЛЬНЫЙ УРОВЕНЬ (исправлен в 2.1) ─────────────
   max_level  = 0
   can_delete = false
   FOR (role, perm) IN cands:
       lvl = 0
       IF perm.full_access:                              lvl = 4
       ELIF perm.editor:                                 lvl = 3   // ← редактор (3)
       ELIF perm.author AND document.author_id = user.id: lvl = 2 // ← автор (2)
       ELIF perm.reader:                                 lvl = 1
       max_level  = MAX(max_level, lvl)                 // Правило 5.3.2
       can_delete = can_delete OR perm.can_delete       // Правило 5.3.3

   IF max_level = 0:
       RETURN (false, 0, false, NONE)                   // нет права на чтение ⇒ не виден (§2.3)

   ── ШАГ 5. ПЕРЕКЛЮЧАТЕЛИ ТИПА ДОКУМЕНТА ───────────────────────
   dt           = doctype_ref(document.doctype)
   or_enforced  = dt.apply_or_tags
   and_enforced = dt.apply_and_tags

   ── ШАГ 6. ПРАВИЛО «НЕТ ТЕГОВ» ────────────────────────────────
   untagged = ( or_enforced  AND (document.or_tags  IS NULL OR document.or_tags  = ∅) )
           OR ( and_enforced AND (document.and_tags IS NULL OR document.and_tags = ∅) )
   IF untagged:
       IF max_level = 4:
           PROCEED к ШАГУ 9                            // Правило 6.6.5
       ELSE:
           RETURN (false, 0, false, NONE)              // Правила 6.6.1–6.6.4

   ── ШАГ 7. ТЕГ-ПРОВЕРКА ЗАПОЛНЕННЫХ ЗНАЧЕНИЙ ──────────────────
   IF NOT untagged:
       IF NOT check_tags(user.tags, document.or_tags, document.and_tags,
                         or_enforced, and_enforced):
           max_level_via_roles = false                  // пробуем делегирование (ШАГ 8)
       ELSE:
           max_level_via_roles = true
   ELSE:
       max_level_via_roles = true                       // для уровня 4 тег-проверка не нужна

   ── ШАГ 8. ДЕЛЕГИРОВАНИЕ ──────────────────────────────────────
   IF max_level_via_roles:
       PROCEED к ШАГУ 9
   deleg = active_delegation_for(user.id, document.id, now)
   IF deleg IS NOT NULL:
       delegator = load_user(deleg.delegator_id)
       (d_visible, d_level, d_can_delete, _) = resolve_access(delegator, document, now)
       IF d_visible = false:
           RETURN (false, 0, false, NONE)
       level_dl = MIN(deleg.level, d_level)
       delete_dl = deleg.can_delete AND d_can_delete AND deleg.allow_delete
       RETURN (true, level_dl, delete_dl, DELEGATION)   // теги не проверяются (§11.4.4)

   ── ШАГ 9. ФИНАЛ + ПОТОЛОК ПЛАТФОРМЕННОГО РАЗДЕЛА (новое в 2.1) ──
   IF is_platform AND user.is_superadmin = false:       // §4.3.3
       level      = 1                                   // потолок чтения
       can_delete = false
   ELSE:
       can_delete = can_delete OR (level >= 2)          // §5.2.4
   RETURN (true, max_level, can_delete, ROLE)
```

### 16.8. Редактор имеет больше прав, чем Автор (исправление 2.1)

```
Дано:   Пользователь имеет роли с флагами {editor, author} для "notes".
        Документ D1: author_id = другой пользователь.
        Документ D2: author_id = текущий пользователь.
Расчёт для D1:
        editor → lvl 3; author не срабатывает (не свой) → уровень 3.
Расчёт для D2:
        editor → lvl 3 (проверяется раньше); уровень 3.
Результат: в обоих случаях уровень = 3 (редактор). Редактор изменяет/удаляет
           документы любого автора. Автор без флага editor изменяет только свои.
```

### 16.9. Автор без редактора изменяет только своё

Дано:   Пользователь имеет роль только с флагом {author} для "notes".
        Документ D1: author_id = другой пользователь.
        Документ D2: author_id = текущий пользователь.
Расчёт для D1: author не срабатывает (не свой) → уровень 0 → НЕ ВИДИМ.
Расчёт для D2: author → lvl 2 → ВИДИМ, уровень 2, can_delete = true (§5.2.4).

## Требуемые изменения в коде `AccessService`

В соответствии с новой иерархией (Редактор 3 > Автор 2) необходимо изменить два места:

### 1. `backend/app/core/access/schemas.py` — константы уровней

```python
# Уровни доступа (ТЗ §5.1, версия 2.1)
# Иерархия: полный (4) > редактор (3) > автор (2) > читатель (1) > нет (0)
ACCESS_LEVEL_NONE: int = 0
ACCESS_LEVEL_READER: int = 1
ACCESS_LEVEL_AUTHOR: int = 2   # ✅ Было 3, стало 2
ACCESS_LEVEL_EDITOR: int = 3   # ✅ Было 2, стало 3
ACCESS_LEVEL_FULL: int = 4
```

### 2. `backend/app/core/access/service.py` — порядок проверок в `_role_level`

```python
    @staticmethod
    def _role_level(permission: PermissionModel, is_author: bool) -> int:
        """
        Уровень роли (ТЗ §5.1, версия 2.1).

        Иерархия: полный (4) > редактор (3) > автор (2) > читатель (1).
        Редактор имеет более широкие полномочия, чем Автор:
        редактор изменяет/удаляет документы любого автора, автор — только свои.
        Поэтому редактор (3) численно выше автора (2),
        и флаг 'editor' проверяется ДО флага 'author'.
        """
        if permission.full_access:
            return ACCESS_LEVEL_FULL
        # ✅ Редактор (3) проверяется раньше автора и численно выше
        if permission.editor:
            return ACCESS_LEVEL_EDITOR
        # ✅ Автор (2) присваивается только для собственных документов
        if is_author and permission.author:
            return ACCESS_LEVEL_AUTHOR
        if permission.reader:
            return ACCESS_LEVEL_READER
        return ACCESS_LEVEL_NONE
```

**Обоснование изменения порядка:** если пользователь имеет оба флага (`editor` и `author`) и является автором документа, результат должен быть 3 (редактор), а не 2. Проверка `editor` до `author` гарантирует это.
