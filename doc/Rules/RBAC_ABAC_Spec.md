## Система разграничения доступа на основе ролей, разделов и тегов (RBAC + ABAC)
### Cool ERP — формализованное описание
### Версия 2.0

## 0. Изменения относительно версии 1.0

| № | Было (v1.0) | Стало (v2.0) | Раздел |
|---|-------------|--------------|--------|
| 0.1 | Пустой `section_ids` роли = доступ ко **всем** разделам организации | Пустой `section_ids` роли = роль **не даёт никаких прав**. Разделы задаются только явно | §4 |
| 0.2 | Переключатели `apply_or_tags` / `apply_and_tags` — на уровне **роли** (`PermissionModel`) | Переключатели — на уровне **Типа документа** (`DoctypeModel`). Устанавливает только Суперадмин | §7 |
| 0.3 | Пустые теги документа = ограничение не применяется | При включённом применении тегов пустые теги документа = доступ **только** пользователям с **Полным** уровнем. Администраторы и Суперадминистраторы **не освобождаются** | §6.5 |
| 0.4 | Поля `access_by_tags`, `or_tags`, `and_tags`, `no_tags` в `PermissionModel` | **Удаляются** (миграция §14) | §13, §14 |
| 0.5 | Аудит — отложено | **Раздел 12**: аудит конфигурации доступов + аудит доступа к данным (минимум для РФ) | §12 |
| 0.6 | Временные ограничения — отложено | **Раздел 10**: срочные назначения ролей | §10 |
| 0.7 | Делегирование — отложено | **Раздел 11**: делегирование доступа | §11 |
| 0.8 | — | Введено понятие **контракта атрибутов доступа** для любого хранилища документов | §3.3 |

**Принцип версии 2.0:** допускается **только явное управление**. Ни один слой доступа не предоставляет прав «по умолчанию» и не снимает ограничений автоматически.

## 1. Термины и определения

| Термин | Определение |
|--------|-------------|
| **Организация (Тенант)** | Изолированное пространство данных. Каждая запись принадлежит ровно одной Организации. |
| **Пользователь** | Учётная запись, принадлежащая одной Организации. Имеет одно или несколько Назначений Ролей. |
| **Администратор** | Пользователь с `is_admin = true` в своей Организации. |
| **Суперадмин** | Пользователь с `is_superadmin = true`. Видит все Организации. **Не освобождается** от правил тег-фильтрации. |
| **Роль** | Именованный набор: Разделы × Типы документов × Уровни доступа. |
| **Назначение роли (Grant)** | Связь «Пользователь ↔ Роль» с необязательными сроками действия. |
| **Раздел** | Логическое пространство доступа. Не является физической структурой хранения. Задаётся полем `section_id` в записи документа. |
| **Тип документа (doctype)** | Строковый код категории документа (`"invoices"`, `"contracts"`). Несёт глобальные переключатели тег-применимости. |
| **Документ** | Экземпляр данных. Обязан соблюдать **контракт атрибутов доступа** (§3.3). |
| **Тег** | Строка `<пространство>:<значение>` (`регион:сибирь`). |
| **Уровень доступа** | `полный (4)` > `автор (3)` > `редактор (2)` > `читатель (1)` > `нет (0)`. |
| **Полный уровень** | Уровень 4. Включает право вручную управлять тегами документа. |
| **Область доступа** | Совокупность записей, видимых пользователю. Формируется пересечением слоёв: Тенант × Разделы × Типы × Теги, с определением уровня. |
| **Делегирование** | Временная передача конкретных прав на конкретные документы от Делегатора Делегату. |
| **Аудит** | Неизменяемая регистрация фактов изменения настроек доступа и (минимально) фактов изменения данных. |

## 2. Общие принципы

| Принцип | Формулировка |
|---------|--------------|
| 2.1 **Явное управление** | Право возникает только из явно заданных настроек: Разделы в роли, записи Permissions, теги пользователя, теги документа, переключатели Типа документа. Пустое значение **никогда** не означает «всё». |
| 2.2 **Безопасность по умолчанию** | При отсутствии любых из необходимых настроек — доступа нет. Ошибка конфигурации приводит к отсутствию доступа, а не к его появлению. |
| 2.3 **Видимость ≠ уровень** | Разделы и Теги отвечают на вопрос «**существует** ли запись для пользователя». Уровни отвечают на вопрос «**что можно делать** с записью». |
| 2.4 **Приоритет запрета видимости** | Если запись не прошла проверку видимости (Раздел или Теги) — уровень доступа не вычисляется и не применяется, в том числе для Полного уровня, Администраторов и Суперадмина. |
| 2.5 **Отсутствие автоматических исключений** | Администратор и Суперадмин **не** получают доступ автоматически. Для доступа они включаются в соответствующую Роль (и, при необходимости, наделяются тегами). |
| 2.6 **RLS-семантика** | Скрытые записи не возвращаются в списках, не находятся поиском, не участвуют в агрегатах и выгрузках. Пользователь не получает информации об их существовании. |
| 2.7 **Аудируемость** | Каждое изменение настроек доступа регистрируется в неизменяемом журнале (§12.1). |

## 3. Слои разграничения доступа

```
Слой 1: Тенант                    — жёсткая изоляция данных
   ↓
Слой 2: Раздел                    — ВИДИМОСТЬ (явно в роли)
   ↓
Слой 3: Тип документа             — наличие записи Permissions в роли
   ↓
Слой 4: Теги                      — ВИДИМОСТЬ (глобально для Типа документа)
   ↓
Слой 5: Уровень доступа           — ЧТО МОЖНО ДЕЛАТЬ (максимум из ролей)
```

### 3.1. Слой 1 — Тенант

| Правило | Формулировка |
|---------|--------------|
| 3.1.1 | Документ принадлежит ровно одной Организации (`tenant_id`). |
| 3.1.2 | Пользователь видит документы только своей Организации. |
| 3.1.3 | Суперадмин видит документы всех Организаций (в границах своих Ролей, Разделов и Тегов). |
| 3.1.4 | Фильтрация выполняется на уровне SQL, а не в памяти приложения. |

### 3.2. Слой 2 — Раздел

| Правило | Формулировка |
|---------|--------------|
| 3.2.1 | Раздел — логический механизм доступа, не связан с физическим хранением. |
| 3.2.2 | Документ содержит `section_id` — обязательное поле. |
| 3.2.3 | Роль содержит `section_ids` — **явный** список разделов. |
| 3.2.4 | Если `section_ids` роли пуст или `NULL` — **роль не даёт доступа ни к одному документу** (Принцип 2.1). |
| 3.2.5 | Если `section_ids` непуст — документ доступен через роль только при `document.section_id ∈ role.section_ids`. |

### 3.3. Контракт атрибутов доступа

Любое хранилище документов (таблица конкретного Типа документа) **обязано** содержать атрибуты:

| Атрибут | Тип | Обязательность | Назначение |
|---------|-----|----------------|------------|
| `tenant_id` | `UUID` | Да | Слой 1 |
| `section_id` | `UUID` | Да | Слой 2 |
| `author_id` | `UUID` | Да | Уровень «автор» |
| `or_tags` | `ARRAY(VARCHAR)` | Да (допускается `NULL`) | Слой 4, ИЛИ |
| `and_tags` | `ARRAY(VARCHAR)` | Да (допускается `NULL`) | Слой 4, И |

Нарушение контракта делает Тип документа непригодным для включения в Роли. Проверка контракта выполняется при создании Типа документа.

### 3.4. Слой 3 — Тип документа

| Правило | Формулировка |
|---------|--------------|
| 3.4.1 | Для Типа документа в роли существует запись `Permission` с набором уровней. |
| 3.4.2 | Если ни одна активная роль не имеет записи `Permission` для `document.doctype` — доступа нет. |
| 3.4.3 | Допустимые для роли Типы документов фильтруются по Организации роли через M2M `doctype_tenants`. |

### 3.5. Слой 4 — Теги

См. §6. Переключатели применимости — на уровне Типа документа (§7).

### 3.6. Слой 5 — Уровень доступа

См. §5.

## 4. Разделы

### 4.1. Типы Разделов

| Тип | Область | Создание | Удаление |
|-----|---------|----------|----------|
| **Общий (платформенный)** | Все Организации | При инициализации платформы | Запрещено |
| **Общий для организации** | Одна Организация | Автоматически при создании Организации | Запрещено |
| **Произвольный** | Одна Организация | Администратор Организации | Администратор, при отсутствии документов |

### 4.2. Явное требование

| Правило | Формулировка |
|---------|--------------|
| 4.2.1 | Роль без явно заданных `section_ids` является **недействующей**: она не добавляет пользователю никаких прав. |
| 4.2.2 | Интерфейс редактирования Роли обязан отображать предупреждение: «Роль не даёт прав: не заданы Разделы» при пустом `section_ids`. |
| 4.2.3 | Сохранение роли без Разделов **разрешено** (роль может быть заготовкой), но такая роль не участвует в вычислении доступа. |
| 4.2.4 | Для доступа к общедоступному контенту роль должна явно включать Раздел «Общий» и/или «Общий для организации». |

## 5. Уровни доступа

### 5.1. Иерархия

```
4 (полный) > 3 (автор) > 2 (редактор) > 1 (читатель) > 0 (нет доступа)
```

| Уровень | Флаг | Права |
|---------|------|-------|
| **Полный (4)** | `full_access` | Просмотр, создание, изменение любых записей, удаление, **ручное управление тегами доступа** документа |
| **Автор (3)** | `author` | Просмотр + изменение только документов, где `author_id = user.id` |
| **Редактор (2)** | `editor` | Просмотр + изменение любых документов типа |
| **Читатель (1)** | `reader` | Только просмотр |
| **Нет (0)** | — | Запись не существует для пользователя |

### 5.2. Право на удаление

| Правило | Формулировка |
|---------|--------------|
| 5.2.1 | `can_delete` — **независимый флаг**, не входит в иерархию уровней. |
| 5.2.2 | Может быть установлен при любом уровне, включая «читатель». |
| 5.2.3 | Итог по пользователю — логическое **ИЛИ** по всем прошедшим роли. |

### 5.3. Разрешение конфликтов между ролями

| Правило | Формулировка |
|---------|--------------|
| 5.3.1 | Роли задают «что **разрешено**». |
| 5.3.2 | При нескольких уровнях для одного Типа документа применяется **максимальный** уровень. |
| 5.3.3 | `can_delete` объединяется по **ИЛИ**. |
| 5.3.4 | Конфликты видимости (Разделы, Теги) разрешаются **не** максимумом, а правилом «прошла хотя бы одна роль по разделам И пройдена глобальная тег-проверка» (§8). |

## 6. Теги доступа (ABAC)

### 6.1. Назначение и семантика

| Правило | Формулировка |
|---------|--------------|
| 6.1.1 | Теги определяют **видимость** отдельного экземпляра документа. |
| 6.1.2 | Теги равноправны с Разделами: оба отвечают на вопрос «существует ли запись для пользователя». |
| 6.1.3 | Теги **приоритетнее** уровней доступа: пользователь с Полным уровнем не видит документ, не прошедший тег-проверку. |
| 6.1.4 | Скрытые записи не возвращаются списками, поиском, выгрузками; не участвуют в итогах и агрегатах. |

### 6.2. Формат тега

| Правило | Формулировка |
|---------|--------------|
| 6.2.1 | Формат: `<пространство>:<значение>`. |
| 6.2.2 | Разделитель — двоеточие. Пробелы в пространстве и значении запрещены. |
| 6.2.3 | Регистр значим: `Регион:Сибирь` ≠ `регион:сибирь`. |
| 6.2.4 | Вложенность (`a:b:c`) в версии 2.0 **не поддерживается**. |

**Примеры:**

```
регион:сибирь          регион:центр           регион:дальнийвосток
отдел:бухгалтерия      отдел:юридический      отдел:продажи
проект:альфа           проект:бета
гриф:секретно          гриф:дляслужебногопользования
уровеньдоступа:высший  уровеньдоступа:средний
контрагент:газпром
```

### 6.3. Теги пользователя

| Правило | Формулировка |
|---------|--------------|
| 6.3.1 | Хранятся в `UserModel.tags` типа `ARRAY(VARCHAR)`. |
| 6.3.2 | Присваивает **только** Администратор Организации или Суперадмин. |
| 6.3.3 | Пользователь **не** может изменять собственные теги. |
| 6.3.4 | Присвоение тегов семантически аналогично включению в группу доступа. |
| 6.3.5 | Видимость тегов пользователя: сам пользователь (свои), Администратор своей Организации, Суперадмин. |

### 6.4. Теги документа

| Правило | Формулировка |
|---------|--------------|
| 6.4.1 | Хранятся в `or_tags` и `and_tags` записи документа (`ARRAY(VARCHAR)`, допускается `NULL`). |
| 6.4.2 | Ручное установление тегов доступно **только**: Администратору Организации, Суперадмину, пользователям с **Полным** уровнем для данного Типа документа. |
| 6.4.3 | **Автор** документа не имеет права устанавливать теги (если не обладает Полным уровнем). |
| 6.4.4 | **Редактор** документа не имеет права устанавливать теги (если не обладает Полным уровнем). |
| 6.4.5 | Допускается установление тегов **автоматически по событию** (бизнес-логика). Ручное и автоматическое управление не противоречат принципу 2.1, так как каждое значение явно записывается в документ. |
| 6.4.6 | Видимость тегов документа: любой пользователь, которому документ виден. |

### 6.5. Два поля тегов документа

#### 6.5.1. `or_tags` — фильтр по совпадению (ИЛИ)

| Правило | Формулировка |
|---------|--------------|
| 6.5.1.1 | При применении: пользователь должен иметь **хотя бы один** тег из `doc.or_tags`. |
| 6.5.1.2 | Семантика — **белый список** круга возможных пользователей. |
| 6.5.1.3 | Если `doc.or_tags` пуст/`NULL` при включённом применении — действует §6.6. |

#### 6.5.2. `and_tags` — обязательный допуск (И)

| Правило | Формулировка |
|---------|--------------|
| 6.5.2.1 | При применении: пользователь должен иметь **все** теги из `doc.and_tags`. |
| 6.5.2.2 | Семантика — **безусловное отнятие** доступа у всех, кто не имеет требуемого допуска (например `гриф:секретно`, `уровеньдоступа:высший`). |
| 6.5.2.3 | Если `doc.and_tags` пуст/`NULL` при включённом применении — действует §6.6. |

### 6.6. Правило «нет тегов при включённом применении»

> **Правило 6.6.1.** Если для Типа документа включено применение `or_tags` и при этом `doc.or_tags` пуст/`NULL` — документ виден **только** пользователям, чей итоговый уровень для этого Типа документа равен **4 (полный)**.

> **Правило 6.6.2.** Если для Типа документа включено применение `and_tags` и при этом `doc.and_tags` пуст/`NULL` — документ виден **только** пользователям с уровнем **4 (полный)**.

> **Правило 6.6.3.** Достаточно срабатывания **любого** из условий 6.6.1 / 6.6.2 для ограничения круга видимых пользователей уровнем 4.

> **Правило 6.6.4.** Администраторы и Суперадминистраторы **не освобождаются** от правил 6.6.1–6.6.3. Для получения доступа они включаются в Роль, дающую уровень 4 для данного Типа документа (и, при необходимости, наделяются тегами).

> **Правило 6.6.5.** Для пользователей с уровнем 4 тег-проверка по пустым полям **не выполняется** (проверять нечего). Это обеспечивает им возможность увидеть документ и назначить ему теги.

**Замысел правила:** документ без тегов при включённом тег-режиме является «неоформленным». Его видит только тот, кто обязан его оформить — пользователь с Полным уровнем, обладающий правом установки тегов (§6.4.2).

### 6.7. Проверка тегов для заполненных значений

```
ФУНКЦИЯ check_tags(user_tags, doc_or_tags, doc_and_tags, or_enforced, and_enforced):

  ШАГ 1: and_tags (обязательный допуск)
  ЕСЛИ and_enforced И doc_and_tags НЕ ПУСТ:
      ЕСЛИ НЕ (doc_and_tags ⊆ user_tags):
          → ОТКАЗ

  ШАГ 2: or_tags (белый список)
  ЕСЛИ or_enforced И doc_or_tags НЕ ПУСТ:
      ЕСЛИ user_tags ∩ doc_or_tags = ∅:
          → ОТКАЗ

  → ТЕГ-ПРОВЕРКА ПРОЙДЕНА
```

**Формальная запись:**

```
visible_by_tags =
    ( ¬and_enforced ∨ doc_and_tags = ∅ ∨ doc_and_tags ⊆ user_tags )
  ∧ ( ¬or_enforced  ∨ doc_or_tags  = ∅  user_tags ∩ doc_or_tags ≠ ∅ )
```

### 6.8. Действие тегов на заполненные документы — для всех без исключений

| Правило | Формулировка |
|---------|--------------|
| 6.8.1 | Для документа с заполненными (при включённом применении) тегами тег-проверка выполняется для **всех** пользователей, включая имеющих уровень 4, Администраторов и Суперадмина. |
| 6.8.2 | Исключение: активное Делегирование на конкретный документ (§11) — единственная легитимная причина пропуска тег-проверки. |
| 6.8.3 | Следствие: если ни один активный пользователь не удовлетворяет тегам документа, документ становится **недоступным никому** («сирота»). Обязателен отчёт-детектор (§12.1.6, отчёт C). |

## 7. Переключатели применимости тегов на уровне Типа документа

### 7.1. Модель

| Поле `DoctypeModel` | Тип | По умолчанию | Описание |
|---------------------|-----|--------------|----------|
| `apply_or_tags` | `BOOL` | `false` | Применять фильтр по `doc.or_tags` для всех документов данного Типа |
| `apply_and_tags` | `BOOL` | `false` | Применять фильтр по `doc.and_tags` для всех документов данного Типа |
| `audit_read` | `BOOL` | `false` | Регистрировать события **чтения** документов данного Типа (§12.2.4) |

### 7.2. Правила

| Правило | Формулировка |
|---------|--------------|
| 7.2.1 | Переключатели задаются **только** в справочнике Типов документов. |
| 7.2.2 | Изменяет переключатели **только Суперадмин**. Администратор Организации — только чтение. |
| 7.2.3 | Переключатели **глобальны** для Типа документа и едины для всех Организаций и всех Ролей. |
| 7.2.4 | Значение по умолчанию — `false`: тег-режим не включается пока Суперадмин явно его не включит. |
| 7.2.5 | Изменение переключателя является изменением настроек доступа и подлежит аудиту (§12.1) с перечнем затронутых Организаций. |
| 7.2.6 | В интерфейсе Роли (вкладка «Полномочия») переключатели **не отображаются** — они не являются атрибутом роли. |

### 7.3. Последствия включения

| Последствие | Описание |
|-------------|----------|
| 7.3.1 | Все существующие документы данного Типа **без тегов** немедленно становятся видимыми только пользователям с уровнем 4 (§6.6). |
| 7.3.2 | Требуется подтверждение действия в интерфейсе с текстом о последствиях и о числе затронутых документов. |
| 7.3.3 | После включения рекомендуется сформировать отчёт C (§12.1.6) и выполнить разметку документов. |

## 8. Полный алгоритм вычисления доступа

### 8.1. Формальное описание

```
ВХОД:
  user      — пользователь: tenant_id, is_superadmin, tags, активные Назначения Ролей
  document  — документ: tenant_id, doctype, section_id, author_id, or_tags, and_tags
  now       — текущее время (UTC)

ВЫХОД:
  visible    : bool          — существует ли запись для пользователя
  level      : 0..4          — итоговый уровень доступа
  can_delete : bool          — право на удаление
  source     : ROLE | DELEGATION
```

### 8.2. Псевдокод

```
FUNCTION resolve_access(user, document, now) -> (visible, level, can_delete, source):

  ── ШАГ 1. ТЕНАНТ ─────────────────────────────────────────────
  IF document.tenant_id ≠ user.tenant_id AND user.is_superadmin = false:
      RETURN (false, 0, false, NONE)

  ── ШАГ 2. ДЕЙСТВУЮЩИЕ НАЗНАЧЕНИЯ РОЛЕЙ ──────────────────────
  grants = SELECT g FROM user_role_grants g
           WHERE g.user_id = user.id
             AND (g.valid_from  IS NULL OR g.valid_from  ≤ now)
             AND (g.valid_until IS NULL OR g.valid_until >  now)
  IF grants = ∅:
      roles = []                      // обратная совместимость: user.role_ids
  ELSE:
      roles = load_roles(grants.role_ids)

  ── ШАГ 3. КАНДИДАТЫ-РОЛИ: ЯВНЫЕ РАЗДЕЛЫ + PERMISSION ─────────
  cands = []
  FOR role IN roles:
      IF role.section_ids IS NULL OR role.section_ids = ∅:
          CONTINUE                                   // Правило 4.2.1
      IF document.section_id ∉ role.section_ids:
          CONTINUE                                   // Правило 3.2.5
      perm = role.permissions.find(doctype = document.doctype)
      IF perm IS NULL:
          CONTINUE                                   // Правило 3.4.2
      cands.append((role, perm))

  ── ШАГ 4. МАКСИМАЛЬНЫЙ УРОВЕНЬ (без учёта тегов) ─────────────
  max_level  = 0
  can_delete = false
  FOR (role, perm) IN cands:
      lvl = 0
      IF perm.full_access:                              lvl = 4
      ELIF perm.author AND document.author_id = user.id: lvl = 3
      ELIF perm.editor:                                 lvl = 2
      ELIF perm.reader:                                 lvl = 1
      max_level  = MAX(max_level, lvl)                 // Правило 5.3.2
      can_delete = can_delete OR perm.can_delete       // Правило 5.3.3

  ── ШАГ 5. ПЕРЕКЛЮЧАТЕЛИ ТИПА ДОКУМЕНТА ───────────────────────
  dt           = doctype_ref(document.doctype)
  or_enforced  = dt.apply_or_tags
  and_enforced = dt.apply_and_tags

  ── ШАГ 6. ПРАВИЛО «НЕТ ТЕГОВ» ────────────────────────────────
  untagged = ( or_enforced  AND (document.or_tags  IS NULL OR document.or_tags  = ∅) )
          OR ( and_enforced AND (document.and_tags IS NULL OR document.and_tags = ∅) )

  IF untagged:
      IF max_level = 4:
          RETURN (true, 4, can_delete, ROLE)          // Правило 6.6.5
      ELSE:
          RETURN (false, 0, false, NONE)              // Правила 6.6.1–6.6.4

  ── ШАГ 7. ТЕГ-ПРОВЕРКА ЗАПОЛНЕННЫХ ЗНАЧЕНИЙ ──────────────────
  IF max_level ≥ 1:
      IF NOT check_tags(user.tags, document.or_tags, document.and_tags,
                        or_enforced, and_enforced):
          // роли не прошли теги — пробуем делегирование (ШАГ 8)
          max_level_via_roles = false
      ELSE:
          max_level_via_roles = true
  ELSE:
      max_level_via_roles = false

  ── ШАГ 8. ДЕЛЕГИРОВАНИЕ ──────────────────────────────────────
  IF max_level_via_roles:
      RETURN (true, max_level, can_delete, ROLE)

  deleg = active_delegation_for(user.id, document.id, now)
  IF deleg IS NOT NULL:
      delegator = load_user(deleg.delegator_id)
      (d_visible, d_level, d_can_delete, _) = resolve_access(delegator, document, now)
      IF d_visible = false:
          RETURN (false, 0, false, NONE)              // делегатор утратил право
      level_dl = MIN(deleg.level, d_level)
      delete_dl = deleg.can_delete AND d_can_delete AND deleg.allow_delete
      RETURN (true, level_dl, delete_dl, DELEGATION)  // теги не проверяются (§11.4.4)

  ── ШАГ 9. ФИНАЛ ──────────────────────────────────────────────
  RETURN (false, 0, false, NONE)
```

### 8.3. Таблица решений

| Условие | Результат |
|---------|-----------|
| Тенант не совпадает, пользователь не Суперадмин | **НЕ ВИДИМ** |
| Нет активных Назначений Ролей | **НЕ ВИДИМ** |
| `role.section_ids` пуст/`NULL` | Роль отклонена (прав не даёт) |
| `document.section_id ∉ role.section_ids` | Роль отклонена |
| Нет `Permission` для `doctype` в роли | Роль отклонена |
| Все роли отклонены | **НЕ ВИДИМ** |
| Включено применение тегов И соответствующие теги документа пустЫ И уровень < 4 | **НЕ ВИДИМ** |
| Включено применение тегов И теги заполнены И тег-проверка не пройдена И нет делегирования | **НЕ ВИДИМ** |
| Максимальный уровень = 0 | **НЕ ВИДИМ** |
| Максимальный уровень ≥ 1 и видимостью не запрещено | **ВИДИМ**, уровень = максимум |
| `can_delete = true` хотя бы в одной прошедшей роли | Удаление **разрешено** |
| Есть активное делегирование на документ и делегатор имеет доступ | **ВИДИМ** через делегирование, уровень = `MIN(делег.уровень, уровень делегатора)` |

## 10. Временные ограничения доступа (срочные назначения)

### 10.1. Назначение

Покрытие сценариев: замещение на время отпуска/больничного, проектная работа с ограниченным сроком, сезонные сотрудники, внешние исполнители, доступ на время проверки/ревизии.

### 10.2. Модель данных

```
Таблица user_role_grants
  id             UUID  PK
  tenant_id      UUID  NOT NULL
  user_id        UUID  NOT NULL
  role_id        UUID  NOT NULL
  valid_from     TIMESTAMPTZ  NULL     -- NULL = действует с момента назначения
  valid_until    TIMESTAMPTZ  NULL     -- NULL = бессрочно
  granted_by     UUID  NOT NULL        -- кто назначил
  reason         VARCHAR(255) NULL     -- основание (рекомендуется заполнять)
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
  revoked_at     TIMESTAMPTZ NULL      -- досрочный отзыв
  revoked_by     UUID NULL
```

### 10.3. Правила

| Правило | Формулировка |
|---------|--------------|
| 10.3.1 | Все времена хранятся и сравниваются в **UTC**. |
| 10.3.2 | Назначение активно, если `(valid_from IS NULL OR valid_from ≤ now)` И `(valid_until IS NULL OR valid_until > now)` И `revoked_at IS NULL`. |
| 10.3.3 | Истечение срока определяется **на лету**, при вычислении доступа. Отдельный планировщик для прекращения доступа **не требуется**. |
| 10.3.4 | Ночной регламентный процесс выполняет только: уведомления и проставление фактов истечения для отчётности. |
| 10.3.5 | Уведомления: за 7, 1 календарный день и в день истечения — назначенному пользователю и `granted_by`. |
| 10.3.6 | При `valid_until` более 180 суток интерфейс выдаёт предупреждение (не запрет). |
| 10.3.7 | Досрочный отзыв возможен Администратором Организации и Суперадмином; фиксируется `revoked_at`, `revoked_by`. |
| 10.3.8 | Каждое назначение, изменение срока и отзыв — событие аудита (§12.1). |
| 10.3.9 | `UserModel.role_ids` сохраняется как денормализованный кэш активных ролей для совместимости; источником истины является `user_role_grants`. |

### 10.4. Интерфейс

| Место | Элемент |
|-------|---------|
| Редактирование пользователя | У каждой роли: переключатель «срочное», поля `valid_from`, `valid_until`, `reason` |
| Список пользователей | Признак «срочное» и остаток дней до истечения |
| Список ролей | Число активных и срочных назначений |

## 11. Делегирование доступа

### 11.1. Назначение

Временная передача прав на **конкретные документы** от одного пользователя другому: отпуск, болезнь, командировка, совместная работа, передача дел при увольнении.

### 11.2. Модель данных

```
Таблица access_delegations
  id                UUID  PK
  tenant_id         UUID  NOT NULL
  delegator_id      UUID  NOT NULL     -- кто передаёт
  delegate_id       UUID  NOT NULL     -- кому передают
  doctype           VARCHAR(128) NOT NULL
  document_ids      UUID[] NOT NULL     -- замороженный список документов
  level             SMALLINT NOT NULL   -- 1..3 (читатель/редактор/автор)
  allow_delete      BOOLEAN NOT NULL DEFAULT false
  valid_from        TIMESTAMPTZ NOT NULL
  valid_until       TIMESTAMPTZ NOT NULL
  reason            VARCHAR(500) NOT NULL
  status            VARCHAR(16) NOT NULL  -- ACTIVE | REVOKED | EXPIRED
  requires_approval BOOLEAN NOT NULL DEFAULT false
  approved_by       UUID NULL
  created_by        UUID NOT NULL
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
  revoked_at        TIMESTAMPTZ NULL
  revoked_by        UUID NULL
```

### 11.3. Ограничения (жёсткие)

| Правило | Формулировка |
|---------|--------------|
| 11.3.1 | Делегируемый уровень **не может превышать** уровень Делегатора на момент создания и на момент каждого обращения. |
| 11.3.2 | Делегирование уровня **4 (полный) запрещено** всегда: право управлять тегами не передаётся. |
| 11.3.3 | `valid_until` **обязателен**. Бессрочное делегирование запрещено. |
| 11.3.4 | Максимальный срок — **30 суток** (настраиваемый предел). |
| 11.3.5 | `reason` обязателен, минимальная длина 10 символов. |
| 11.3.6 | `document_ids` **замораживается** в момент создания: последующее создание документов в область делегирования не входит. |
| 11.3.7 | Лимит на одно делегирование — не более **200 документов** (настраиваемо). |
| 11.3.8 | Самоделегирование запрещено. Делегирование пользователю другой Организации запрещено. |
| 11.3.9 | **Ределегирование запрещено**: Делегат не может передать полученные права дальше. |
| 11.3.10 | `allow_delete = true` требует подтверждения Администратором Организации (`requires_approval = true`). |
| 11.3.11 | Делегирование **не наследуется** и не переживает удаление/отзыв роли Делегатора: при утрате Делегатором прав делегирование автоматически перестаёт действовать (ШАГ 8, §8.2). |
| 11.3.12 | Отзыв: немедленно, возможен Делегатором, Администратором Организации, Суперадмином. |
| 11.3.13 | Каждый факт использования делегирования (доступ к документу через `source = DELEGATION`) регистрируется в аудите данных (§12.2). |

### 11.4. Взаимодействие с тегами

| Правило | Формулировка |
|---------|--------------|
| 11.4.1 | Делегирование выдаётся на **конкретный список документов**, а не на фильтр. |
| 11.4.2 | Делегату **не требуется** обладать тегами документов: права выдаются явно и ограничены списком и сроком. |
| 11.4.3 | Это единственное легитимное основание пропуска тег-проверки (§6.8.2). |
| 11.4.4 | Пропуск тег-проверки действует **только** для документов из `document_ids` и **только** в окне `valid_from … valid_until`. |
| 11.4.5 | Делегирование не может быть выдано на документ, к которому Делегатор не имеет доступа в момент создания. |

### 11.5. Жизненный цикл

```
СОЗДАНИЕ → (требуется подтверждение?) → АКТИВНО → (ОТЗЫВ | ИСТЕЧЕНИЕ | УТРАТА ПРАВ ДЕЛЕГАТОРОМ) → НЕЙТРАЛЬНО
```

### 11.6. Интерфейс

| Место | Элемент |
|-------|---------|
| Список документов | Действие «Делегировать» для выбранных документов (доступно при уровне ≥ 1) |
| Личный кабинет | «Мои делегирования» (выданные) и «Делегировано мне» |
| Администрирование | Список делегирований Организации, отзыв, подтверждение `allow_delete` |

## 12. Аудит

### 12.1. Аудит конфигурации доступов

#### 12.1.1. Что регистрируется

| Объект изменения (`subject_type`) | События | «Кому изменено» (`affected_user_ids`) |
|-----------------------------------|---------|--------------------------------------|
| `ROLE` | CREATE, UPDATE, DELETE | Все пользователи Организации с этой ролью (вычисляется при сохранении) |
| `ROLE_PERMISSION` | GRANT, REVOKE (изменение уровней/`can_delete`) | То же |
| `ROLE_SECTION` | ADD, REMOVE | То же |
| `USER_ROLE` (grant) | GRANT, REVOKE, RESCHEDULE | Назначенный пользователь |
| `USER_TAGS` | ADD, REMOVE | Сам пользователь |
| `DOCTYPE_POLICY` | UPDATE (`apply_or_tags`, `apply_and_tags`, `audit_read`) | Все пользователи Организаций, для которых доступен Тип документа |
| `SECTION` | CREATE, RENAME, DELETE | Пользователи Ролей, включающих Раздел |
| `DELEGATION` | CREATE, REVOKE, EXPIRE | Делегат |

#### 12.1.2. Модель данных

```
Таблица access_audit_log  (append-only)
  id                UUID  PK
  tenant_id         UUID  NULL          -- NULL для платформенных изменений
  occurred_at       TIMESTAMPTZ NOT NULL DEFAULT now()
  request_id        UUID  NOT NULL      -- группировка одного логического сохранения
  actor_id          UUID  NOT NULL
  actor_name        VARCHAR(255) NOT NULL  -- денормализовано
  actor_is_superadmin BOOLEAN NOT NULL
  subject_type      VARCHAR(24) NOT NULL
  subject_id        UUID  NULL
  subject_name      VARCHAR(255) NULL      -- денормализовано
  affected_user_ids UUID[]  NULL
  action            VARCHAR(16) NOT NULL   -- CREATE|UPDATE|DELETE|GRANT|REVOKE|ADD|REMOVE
  changes           JSONB   NOT NULL       -- структурированный дифф
  ip                INET    NULL
  user_agent        TEXT    NULL
```

Формат `changes`:

```json
{
  "fields": {
    "reader": { "from": false, "to": true },
    "editor": { "from": true,  "to": false }
  },
  "arrays": {
    "section_ids": { "added": ["11111111-…"], "removed": ["22222222-…"] },
    "tags":        { "added": ["регион:сибирь"], "removed": [] }
  }
}
```

#### 12.1.3. Требования неизменяемости

| Правило | Формулировка |
|---------|--------------|
| 12.1.3.1 | Таблица **append-only**: прикладные операции `UPDATE` и `DELETE` не предусмотрены ни в CRUD, ни в API. |
| 12.1.3.2 | Пользователь БД, используемый приложением для записи в журнал, имеет привилегии только `INSERT` и `SELECT`. |
| 12.1.3.3 | Целостность обеспечивается хеш-цепочкой: `record_hash = SHA256(prev_hash ‖ каноническое_представление_записи)`. |
| 12.1.3.4 | Удаление записей допускается только регламентным процессом ретенции (§12.1.5) и также фиксируется в журнале. |

#### 12.1.4. Точки регистрации

Регистрация выполняется в **сервисном слое** в той же транзакции, что и само изменение (единый `commit` — в соответствии с правилами проекта). Один вызов сервиса сохранения = один `request_id` = одна или несколько записей журнала.

#### 12.1.5. Ретенция

| Категория | Срок |
|-----------|------|
| Аудит конфигурации доступов | **не менее 3 лет** |
| Подтверждение формирования отчётов | 1 год |

#### 12.1.6. Отчёты

**Отчёт A — Карта доступов (срез на момент формирования)**

Область: одна Организация (Администратор) или все (Суперадмин).

| Представление | Колонки |
|---------------|---------|
| **A1. Сводная по пользователям** | `пользователь_id`, `имя`, `организация`, `теги`, `роли` (с сроками), `разделы_итог`, `типы_документов_итог`, `признак_срочного_доступа` |
| **A2. Матрица «пользователь × тип документа»** | строки — пользователи; колонки — Типы документов; ячейка — `уровень` + `can_delete` + `ограничено_тегами: да/нет` |
| **A3. Детальная** | `пользователь_id`, `имя`, `doctype`, `level`, `can_delete`, `section_ids_роли`, `apply_or_tags`, `apply_and_tags`, `теги_пользователя`, `источник` (ROLE/DELEGATION) |

Форматы: `JSON` (машиночитаемый), `XLSX`, `CSV`. В интерфейсе — матричное представление A2 с фильтрами по Организации, Роли, Типу документа.

**Отчёт B — Изменения за период**

Фильтры: период (обязателен), Организация, Актор, `subject_type`, адресат (`target_user_id`), действие.

| Колонка | Содержание |
|---------|-----------|
| `occurred_at` | Дата и время, ISO 8601, UTC |
| `actor` | `имя (id)` |
| `action` | CREATE / UPDATE / DELETE / GRANT / REVOKE / ADD / REMOVE |
| `subject` | `тип · имя · id` |
| `affected_users` | Список «кому изменено»: `имя (id)`, при большом числе — количество + раскрытие |
| `field` | Изменённое поле / элемент массива |
| `from` → `to` | Предыдущее и новое значение |
| `request_id` | Группировка: одно сохранение = одна группа строк |
| `ip`, `user_agent` | При наличии |

Сводный блок отчёта: количество изменений по действиям, по Акторам, по типам объектов; топ адресатов изменений.

Форматы: `XLSX` (лист «Детали» + лист «Сводка»), `CSV`, `JSON`.

**Отчёт C — Контроль «сирот» и неоформленных документов** (обязательный, регламентный, ежедневный)

| Раздел | Содержание |
|--------|-----------|
| **C1. Неоформленные** | Документы Типов с включённым применением тегов, у которых соответствующие теги пусты (видны только уровню 4). Колонки: `doctype`, `организация`, `раздел`, `документ`, `создан`, `автор` |
| **C2. Сироты** | Документы, для которых **ни один** активный пользователь не удовлетворяет тегам. Колонки: те же + `причина` (`or_tags` не совпали / `and_tags` не совпали) |
| **C3. Недействующие роли** | Роли с пустым `section_ids` (не дают прав). Колонки: `роль`, `организация`, `назначена_пользователям: кол-во` |

#### 12.1.7. Доступ к отчётам

| Отчёт | Админ Организации | Суперадмин |
|-------|:-----------------:|:----------:|
| A, B, C — своя Организация | ✅ | ✅ |
| A, B, C — все Организации | ❌ | ✅ |

### 12.2. Аудит доступа к данным

#### 12.2.1. Правовые основания (РФ)

> Приведённый перечень задаёт **минимум**. Окончательный состав событий и сроки хранения утверждает ответственный за обработку персональных данных совместно с юридической службой с учётом категории информационной системы, уровня защищённости и отрасли.

| Нормативный акт | Что требует | Последствие для системы |
|-----------------|-------------|--------------------------|
| **ФЗ-152 «О персональных данных»**, ст. 18.1 | Меры по обеспечению безопасности ПДн, включая недопущение несанкционированного доступа и выявление инцидентов | Регистрация фактов доступа к записям, содержащим ПДн |
| **Приказ ФСТЭК России № 21** (ИСПДн), **№ 17** (ГИС) | Регистрация событий безопасности, затрагивающих ПДн; защита журналов от модификации; хранение журналов (ориентировочно **не менее 1 года**, уточняется по уровню защищённости) | Неизменяемый журнал, защита прав доступа, ретенция |
| **ФЗ-149 «Об информации…»**, ст. 16, 17 | Безопасность информации, обнаружение фактов несанкционированного доступа | Фиксация субъекта и времени операции |
| **ФЗ-402 «О бухгалтерском учёте»**, ст. 10 | Хранение первичных документов и регистров **не менее 5 лет**, воспроизводимость учётных данных | Регистрация изменений и удалений учётных документов, срок **5 лет** |
| **ФЗ-115 (ПОД/ФТ)**, ст. 7 — при применении | Хранение информации об операциях **не менее 5 лет** | Ретенция 5 лет для соответствующих категорий |
| **ТК РФ**, ст. 86–90 | Обработка ПД работников, ограниченность доступа | Подтверждение круга лиц, имевших доступ |
| **ФЗ-63 «Об электронной подписи»** | Подтверждение субъекта и времени операции при использовании ЭП | Фиксация `actor_id` и `occurred_at` |

#### 12.2.2. Вывод о необходимости

| Тип события | Обязательность | Обоснование |
|-------------|----------------|-------------|
| **CREATE / UPDATE / DELETE** (запись) | **Обязательно для всех Типов документов** | ФЗ-402 ст. 10, ФЗ-152 ст. 18.1, Приказы ФСТЭК. Низкая интенсивность, высокая доказательная ценность |
| **READ** (чтение) | **Выборочно** | Требуется для категорий с ПДн и конфиденциальной информацией; сплошное логирование чтений нерационально по объёму |
| **EXPORT / PRINT** (выгрузка, печать) | **Желательно** | Основной канал утечки; фиксируется там же, где READ |
| **Использование делегирования** | **Обязательно** | Правило 11.3.13 |

#### 12.2.3. Минимальная достаточная реализация

```
Таблица data_audit_log  (append-only)
  id             UUID  PK
  tenant_id      UUID  NOT NULL
  occurred_at    TIMESTAMPTZ NOT NULL DEFAULT now()
  actor_id       UUID  NOT NULL
  actor_name     VARCHAR(255) NOT NULL
  action         VARCHAR(16) NOT NULL   -- CREATE|UPDATE|DELETE|READ|EXPORT|PRINT
  doctype        VARCHAR(128) NOT NULL
  document_id    UUID  NOT NULL
  document_label VARCHAR(255) NULL      -- наименование/номер, без ПДн
  changed_fields JSONB  NULL            -- для UPDATE: {field: {from, to}}
  via_delegation BOOLEAN NOT NULL DEFAULT false
  delegation_id  UUID  NULL
  ip             INET  NULL
  user_agent     TEXT  NULL
  prev_hash      CHAR(64) NOT NULL
  record_hash    CHAR(64) NOT NULL
```

| Правило | Формулировка |
|---------|--------------|
| 12.2.3.1 | События `CREATE`, `UPDATE`, `DELETE` регистрируются для **всех** Типов документов. |
| 12.2.3.2 | События `READ`, `EXPORT`, `PRINT` регистрируются только для Типов документов с `DoctypeModel.audit_read = true` (устанавливает Суперадмин). |
| 12.2.3.3 | В `changed_fields` хранятся **метаданные** изменённых полей. Значения ПДн **не записываются** в открытом виде; при необходимости — в зашифрованном виде отдельным механизмом. Журнал не должен сам становиться источником утечки. |
| 12.2.3.4 | Целостность — хеш-цепочка `prev_hash → record_hash` (правило 12.1.3.3). |
| 12.2.3.5 | Привилегии прикладного пользователя БД на журнал: только `INSERT`, `SELECT`. |
| 12.2.3.6 | Ретенция: `CREATE/UPDATE/DELETE` — **5 лет**; `READ/EXPORT/PRINT` — **1 год**. |
| 12.2.3.7 | Регистрация выполняется в сервисном слое в той же транзакции, что и операция с данными. |
| 12.2.3.8 | Каждое использование делегирования фиксируется с `via_delegation = true` и `delegation_id`. |

#### 12.2.4. Защита журнала от самого себя

| Мера | Описание |
|------|----------|
| Отдельная схема или отдельный экземпляр БД | Журнал недоступен для бизнес-запросов |
| Разделение учётных записей | Запись — один пользователь (`INSERT`), отчёты — другой (`SELECT`) |
| Отсутствие API изменения | В CRUD журнала реализованы только `create` и `read` |
| Регламентная проверка целостности | Ежедневная сверка цепочки хешей, результат — в отчёт администратору безопасности |

#### 12.2.5. Отчёт по данным

Фильтры: период, Организация, Актор, `doctype`, `document_id`, `action`, `via_delegation`.

Колонки: `occurred_at`, `actor`, `action`, `doctype`, `document`, `изменённые поля (было → стало)`, `через делегирование`, `ip`.

Форматы: `XLSX`, `CSV`, `JSON`.

## 14. Миграция (ручные SQL-скрипты)

| Шаг | Действие |
|-----|----------|
| 1 | `ALTER TABLE public.doctypes ADD COLUMN apply_or_tags BOOLEAN NOT NULL DEFAULT false, ADD COLUMN apply_and_tags BOOLEAN NOT NULL DEFAULT false, ADD COLUMN audit_read BOOLEAN NOT NULL DEFAULT false;` |
| 2 | `ALTER TABLE public.users ADD COLUMN tags VARCHAR(128)[] NULL;` + индекс GIN |
| 3 | Для каждого хранилища документов: `ADD COLUMN or_tags VARCHAR(128)[] NULL, ADD COLUMN and_tags VARCHAR(128)[] NULL;` + индексы GIN |
| 4 | Создать `user_role_grants`; перенести данные из `users.role_ids` как назначения с `valid_until = NULL`; создать триггер/сервисную синхронизацию кэша `role_ids` |
| 5 | Создать `access_delegations`, `access_audit_log`, `data_audit_log`; назначить привилегии `INSERT`/`SELECT` |
| 6 | Удалить устаревшие колонки `PermissionModel`: `access_by_tags`, `or_tags`, `and_tags`, `no_tags` |
| 7 | Регламентный прогон отчёта C для выявления неоформленных документов и недействующих Ролей |
| 8 | Перегенерация API-клиента после изменения схем |

Порядок шагов 1–6 критичен: удаление колонок (шаг 6) выполняется только после вывода из эксплуатации кода, их использующего.

## 15. Риски и митигации

| № | Риск | Митигация |
|---|------|-----------|
| 15.1 | Включение `apply_*_tags` делает все оттегированные документы видимыми только уровню 4 (правило 7.3.1) | Подтверждение с числом затронутых документов; отчёт C1; рекомендация разметить документы до включения |
| 15.2 | «Сироты»: документ с тегами, которых ни у кого нет (§6.8.3) | Ежедневный отчёт C2; уведомление Администраторов Организации |
| 15.3 | Роль без Разделов выглядит настроенной, но не даёт прав (правило 4.2.1) | Предупреждение в интерфейсе Роли; отчёт C3 |
| 15.4 | Производительность тег-фильтрации на больших выборках | Индексы GIN; фильтрация на уровне SQL; денормализация effective-тегов пользователя в сессии/кэше |
| 15.5 | Журнал чтений при включённом `audit_read` на активном Типе документа | Флаг включается точечно; ретенция 1 год; отдельная схема БД |
| 15.6 | Злоупотребление делегированием | Лимиты срока и объёма (§11.3), обязательная причина, запрет уровня 4, подтверждение при `allow_delete`, аудит каждого использования |
| 15.7 | Утечка через сам журнал | Правило 12.2.3.3: метаданные вместо значений ПДн |
| 15.8 | «Break-glass»: суперадмину нужен доступ к документу с тегом, которого у него нет | Штатная процедура: Суперадмин назначает себе требуемый тег — действие полностью аудируется. Исключений из модели не вводится |

## 16. Примеры сценариев

### 16.1. Роль без Разделов не даёт прав

```
Дано:  Роль «Бухгалтер» имеет Permission для "invoices" (reader, editor),
       но section_ids = NULL.
       Пользователь назначена только эта роль.
Решение (§8.2, ШАГ 3): роль отклонена → НЕ ВИДИМ.
Отчёт: роль попадает в C3 «Недействующие роли».
```

### 16.2. Региональный менеджер, теги заполнены

```
Пользователь: tags = ["регион:сибирь"], роль с section_ids ∋ doc.section_id,
              Permission("deals", editor), can_delete = false.
Документ:     doctype = "deals", or_tags = ["регион:сибирь","регион:центр"], and_tags = NULL.
Тип документа: apply_or_tags = true, apply_and_tags = false.
Расчёт:      or_enforced = true, or_tags непусты → §6.6 не срабатывает.
             and_enforced = false → проверка and_tags пропускается.
             or_tags: {регион:сибирь} ∩ {сибирь, центр} ≠ ∅ → пройдено.
Результат:   ВИДИМ, уровень = 2 (редактор), can_delete = false.
```

### 16.3. Документ без тегов при включённом применении

```
Тип документа "fin_reports": apply_or_tags = true.
Документ: or_tags = NULL, and_tags = NULL.

Пользователь А (уровень 2, редактор)      → НЕ ВИДИМ   (§6.6.1)
Пользователь Б (уровень 4, полный)        → ВИДИМ      (§6.6.5) — может назначить теги
Администратор Организации (уровень 2)     → НЕ ВИДИМ   (§6.6.4)
Суперадмин (уровень 2 в роли)             → НЕ ВИДИМ   (§6.6.4)
Суперадмин, включён в роль с полным уровнем → ВИДИМ    (§6.6.4, путь — через Роль)
```

### 16.4. `and_tags` как безусловный допуск

```
Документ: and_tags = ["гриф:секретно"], or_tags = NULL.
Тип документа: apply_and_tags = true, apply_or_tags = false.

Пользователь с tags = ["гриф:секретно", "уровеньдоступа:высший"], уровень 4 → ВИДИМ
Пользователь с tags = [],                      уровень 4 → НЕ ВИДИМ (§6.7, ШАГ 1)
Пользователь с tags = ["гриф:секретно"],       уровень 1 → ВИДИМ, уровень = 1
```

### 16.5. Срочное назначение истекло

```
Назначение: роль «Заместитель», valid_until = 2026-03-01T00:00:00Z.
now = 2026-03-01T00:00:01Z.
Расчёт (§8.2, ШАГ 2): назначение не активно → роль не участвует.
Результат: доступ прекращён немедленно, без участия планировщика.
```

### 16.6. Делегирование при отпуске

```
Делегатор: Иванов, уровень 3 (автор) по "deals", теги ["регион:сибирь"].
Делегат:   Петров, теги [], по "deals" доступа не имеет.
Делегирование: document_ids = [d1, d2, d3], level = 2, allow_delete = false,
               valid_from = 2026-03-02, valid_until = 2026-03-12,
               reason = "Отпуск Иванова, сопровождение сделок".

Обращение Петрова к d1 (or_tags = ["регион:сибирь"]):
  ШАГ 3–7: роли Петрова не дают доступа → max_level = 0.
  ШАГ 8: делегирование активно; Иванов сохраняет доступ к d1;
         level = MIN(2, 3) = 2; теги не проверяются (§11.4.2).
  Результат: ВИДИМ, уровень = 2, source = DELEGATION, запись в data_audit_log
             с via_delegation = true.

Обращение Петрова к d4 (не в списке):
  Результат: НЕ ВИДИМ.

После отзыва роли Иванова (или истечения срока):
  Результат по d1–d3: НЕ ВИДИМ (§11.3.11, §8.2 ШАГ 8).
```
