# Правило №19: Callback-и из модалок в родительскую страницу

Модальные окна (создания и редактирования) **ОБЯЗАТЕЛЬНО** должны принимать от родительской страницы callback-функции (например, `onItemCreated`, `onItemUpdated` или универсальный `onItemSaved`). 

Модалка **НЕ ДОЛЖНА** самостоятельно управлять состоянием списка, показывать toast-уведомления об успехе или вызывать `refetch` на уровне страницы. Она лишь сообщает родителю: «Я выполнила свою задачу, вот результат».

---

### 1. Обоснование (Почему это важно)

1. **Принцип единой ответственности (SRP):** 
   * **Модалка** отвечает только за сбор данных формы, валидацию и отправку мутации на сервер.
   * **Родительская страница** отвечает за список, пагинацию, кэш TanStack Query и UI-обратную связь (тосты, подсветку строк).
2. **Переиспользуемость:** Модалку можно открыть из разных мест (например, создание роли из админ-панели или из карточки пользователя). Если модалка жестко завязана на `refetch` конкретной страницы, её нельзя будет переиспользовать.
3. **Избежание дублирования кода:** Логика "найти запись в полном списке и показать тост с кнопкой Перейти" (Правило №23) пишется один раз в родителе, а не копируется в каждую модалку.

---

### 2. Обязательные требования к реализации

#### 2.1. Передача callback-ов через пропсы
Родительская страница **ОБЯЗАТЕЛЬНО** передает в модалку функции-обработчики. Стандартные названия:
* `onItemCreated` (или `onXxxCreated`) — вызывается после успешного создания.
* `onItemUpdated` (или `onXxxUpdated`) — вызывается после успешного обновления.
* *Альтернатива:* Универсальный `onItemSaved(id, name)`, если логика для создания и обновления идентична.

#### 2.2. Передача необходимых данных
Callback должен принимать минимум данных, необходимых родителю для навигации и подсветки. Обычно это `id` (UUID) и `name` (для отображения в тосте).

#### 2.3. Разделение ответственности за уведомления
* **Модалка** может показывать ошибки валидации формы (внутри инпутов) и ошибки мутации (например, "Сервер недоступен").
* **Родитель** показывает toast об **успешном** сохранении и занимается обновлением списка.

### 3. Примеры кода

#### ✅ ПРАВИЛЬНО: Родительская страница и Модалка

**Родитель (`RolesPage.tsx`):**
```tsx
// ... состояния и хуки ...

// ✅ Обработчик, который мы передаем в модалку
const handleRoleSaved = async (id: string, name: string) => {
  // Здесь вся логика из Правил №23, №24, №25:
  // 1. refetch()
  // 2. Проверка наличия на странице
  // 3. Подсветка или toast с кнопкой "Перейти"
};

return (
  <div>
    {/* ... таблица ... */}

    {/* ✅ Передаем callback в модалку */}
    {editingRole && (
      <EditRoleModal
        key={editingRole.id}
        open={editModalOpen}
        onOpenChange={setEditModalOpen}
        role={editingRole}
        onRoleSaved={handleRoleSaved} // <-- CALLBACK
      />
    )}
  </div>
);
```

**Модалка (`EditRoleModal.tsx`):**
```tsx
interface EditRoleModalProps {
  open: boolean;
  onOpenChange: (open: boolean) => void;
  role: RoleResponseSchema;
  onRoleSaved: (id: string, name: string) => void; // <-- Принимаем callback
}

export function EditRoleModal({ open, onOpenChange, role, onRoleSaved }: EditRoleModalProps) {
  const queryClient = useQueryClient();
  const { toast } = useToast();
  const updateMutation = useUpdateRoleRolesRoleIdPut();

  const onSubmit = async (data: RoleFormData) => {
    try {
      const res = await updateMutation.mutateAsync({ role_id: role.id, data });
      
      // 1. Инвалидация кэша (Правило №24)
      await queryClient.invalidateQueries({ queryKey: ["roles"] });
      
      // 2. Закрытие модалки
      onOpenChange(false);
      
      // 3. Уведомление родителя (Правило №19)
      // Модалка НЕ показывает toast об успехе, она просто передает данные родителю!
      await onRoleSaved(res.data.id, res.data.name); 
      
    } catch (error) {
      // ✅ Модалка сама обрабатывает только ОШИБКИ
      toast({
        variant: "destructive",
        title: "Ошибка",
        description: "Не удалось сохранить роль",
      });
    }
  };

  // ... JSX формы
}
```

#### ❌ НЕПРАВИЛЬНО: Модалка берет на себя задачи родителя

```tsx
//  ГРУБОЕ НАРУШЕНИЕ ПРАВИЛА №19
export function EditRoleModal({ open, onOpenChange, role }: EditRoleModalProps) {
  const { toast } = useToast();
  
  const onSubmit = async (data: RoleFormData) => {
    try {
      await updateMutation.mutateAsync({ role_id: role.id, data });
      
      onOpenChange(false);
      
      // ❌ ОШИБКА: Модалка сама показывает toast об успехе
      toast({ title: "Роль успешно обновлена!" }); 
      
      //  ОШИБКА: Модалка пытается управлять кэшем родителя напрямую 
      // (хотя invalidateQueries допустим, но поиск и подсветка — нет)
      queryClient.setQueryData(["roles"], (oldData) => {
         // ... ручное изменение кэша, что ломает пагинацию ...
      });
      
    } catch (error) { ... }
  };
}
```

### 4. Нюансы и лучшие практики

#### 4.1. Асинхронность callback-ов
Callback от родителя часто содержит асинхронную логику (например, поиск записи по всему списку при пагинации, см. Правило №23). Поэтому в модалке его **ОБЯЗАТЕЛЬНО** нужно вызывать с `await`:
```tsx
// ✅ Правильно
await onRoleSaved(res.data.id, res.data.name);

//  Неправильно (огонь и забыл, может привести к гонке состояний)
onRoleSaved(res.data.id, res.data.name); 
```

#### 4.2. Универсальный vs Разделенные callback-и
Допускаются оба подхода, но они должны быть консистентны в рамках всего проекта:
* **Разделенные:** `onRoleCreated` и `onRoleUpdated`. Удобно, если логика создания и обновления отличается (например, при создании нужно сбросить форму, а при обновлении — нет).
* **Универсальный:** `onRoleSaved(id, name)`. Удобно, если логика идентична (как в нашем случае с подсветкой и умными тостами). *Рекомендуется для Cool ERP.*

### 5. Чек-лист для разработчика

При создании или рефакторинге модального окна проверьте:

- [ ] Принимает ли модалка callback-функцию (`onItemSaved` / `onItemCreated` / `onItemUpdated`) через пропсы?
- [ ] Вызывается ли этот callback в блоке `try` после успешной мутации и закрытия модалки?
- [ ] Используется ли `await` при вызове callback-а?
- [ ] **Отсутствует** ли в модалке вызов `toast({ title: "Успешно..." })` для позитивных сценариев?
- [ ] **Отсутствует** ли в модалке прямая манипуляция состоянием списка родителя (ручное добавление/удаление элементов в кэш)?

Следование этому правилу делает архитектуру приложения чистой и предсказуемой: модалки остаются "глупыми" исполнителями, а родительская страница выступает "умным" координатором пользовательского опыта.
