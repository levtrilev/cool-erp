# Правило №22: Обязательная структура состояний списочной страницы

Каждая списочная CRUD-страница (например, `RolesPage`, `UsersPage`, `TenantsPage`) **ОБЯЗАТЕЛЬНО** должна иметь строго определенный набор React-состояний (`useState`). Это гарантирует единообразие архитектуры, предсказуемое поведение интерфейса и корректную работу поиска, пагинации, модальных окон и подсветки.

---

### 1. Обоснование (Почему это важно)

Отсутствие стандартизации состояний приводит к тому, что каждая страница разрабатывается "по-своему": где-то поиск работает по каждому символу, где-то модалка редактирования хранит только ID и делает лишний запрос, где-то нет подсветки после сохранения. 

Единая структура состояний:
1. **Ускоряет разработку:** Разработчик всегда знает, какие переменные искать в коде.
2. **Обеспечивает UX:** Гарантирует, что на всех страницах работают умный поиск, пагинация и визуальная обратная связь.
3. **Упрощает рефакторинг:** Легко копировать и адаптировать страницы для новых доменов.

---

### 2. Обязательный набор состояний

Каждая списочная страница **ОБЯЗАТЕЛЬНО** должна объявлять следующие группы состояний:

#### 2.1. Поиск (Разделение ввода и запроса)
* `searchInput: string` — значение, которое пользователь вводит в текстовое поле (контролируемый инпут).
* `search: string` — значение, которое фактически отправляется на бэкенд. Обновляется только по нажатию Enter или кнопки "Найти" (Правило №12).

#### 2.2. Пагинация
* `page: number` — текущая страница (обычно начинается с 1).
* `limit: number` — количество записей на странице (константа, обычно 10 или 20).

#### 2.3. Модальные окна (Создание, Редактирование, Удаление)
* `isCreateOpen: boolean` — флаг открытия модалки создания.
* `editModalOpen: boolean` — флаг открытия модалки редактирования.
* `editingXxx: EntitySchema | null` — **полный объект** редактируемой сущности (НЕ просто ID!). Хранение объекта избавляет от необходимости делать лишний запрос `GET /by-id` перед открытием модалки.
* `deleteXxxId: string | null` — ID сущности, которую нужно удалить. Используется для открытия `AlertDialog` (Правило №16).

#### 2.4. Подсветка (Визуальная обратная связь)
* `highlightedXxxId: string | null` — ID сущности, которая была только что создана или обновлена. Используется для подсветки строки желтым цветом (Правило №17).

### 3. Примеры кода

#### ✅ ПРАВИЛЬНО: Полная инициализация состояний

```tsx
import { useState } from "react";
import type { RoleResponseSchema } from "@/api/generated/fastAPI.schemas";

export const RolesPage = () => {
  // ✅ 1. Поиск (разделенный)
  const [searchInput, setSearchInput] = useState("");
  const [search, setSearch] = useState("");

  // ✅ 2. Пагинация
  const [page, setPage] = useState(1);
  const [limit] = useState(10);

  // ✅ 3. Модальные окна
  const [isCreateOpen, setIsCreateOpen] = useState(false);
  const [editModalOpen, setEditModalOpen] = useState(false);
  const [editingRole, setEditingRole] = useState<RoleResponseSchema | null>(null); // Храним объект!
  const [deleteRoleId, setDeleteRoleId] = useState<string | null>(null);

  // ✅ 4. Подсветка
  const [highlightedRoleId, setHighlightedRoleId] = useState<string | null>(null);

  // ... остальная логика и JSX
```

#### ✅ ПРАВИЛЬНО: Использование состояний в обработчиках

```tsx
// Обработчик поиска (срабатывает по Enter или кнопке)
const handleSearch = (e: React.FormEvent) => {
  e.preventDefault();
  setSearch(searchInput); // ✅ Обновляем запрос
  setPage(1); // ✅ Сбрасываем на первую страницу при новом поиске
};

// Обработчик открытия редактирования
const handleEdit = (role: RoleResponseSchema) => {
  setEditingRole(role); // ✅ Передаем весь объект
  setEditModalOpen(true);
};

// Обработчик удаления
const confirmDelete = async () => {
  if (!deleteRoleId) return;
  await deleteMutation.mutateAsync({ role_id: deleteRoleId });
  await refetch(); // Правило №25
  setDeleteRoleId(null); // ✅ Закрываем AlertDialog
};
```

#### ❌ НЕПРАВИЛЬНО: Типичные антипаттерны

**1. Объединение поиска в одну переменную:**
```tsx
// ❌ ОШИБКА: Поиск будет срабатывать на каждый введенный символ, 
// создавая огромную нагрузку на бэкенд и вызывая "мигание" таблицы.
const [search, setSearch] = useState(""); 
```

**2. Хранение только ID для редактирования:**
```tsx
// ❌ ОШИБКА: Придется делать лишний запрос к API, чтобы получить данные роли для модалки.
const [editingRoleId, setEditingRoleId] = useState<string | null>(null); 

// Вместо этого всегда храните объект:
// const [editingRole, setEditingRole] = useState<RoleResponseSchema | null>(null);
```

**3. Отсутствие разделения на `isCreateOpen` и `editModalOpen`:**
```tsx
// ❌ ОШИБКА: Использование одного флага `isModalOpen` и переключателя режимов 
// усложняет логику и приводит к багам с перемонтированием (Правило №20 требует key={id}).
const [isModalOpen, setIsModalOpen] = useState(false);
const [mode, setMode] = useState<'create' | 'edit'>('create');
```

### 4. Нюансы и рекомендации

#### 4.1. Именование переменных
Всегда используйте суффикс, соответствующий домену. Если страница называется `UsersPage`, состояния должны быть `editingUser`, `deleteUserId`, `highlightedUserId`. Это критически важно при работе с несколькими доменами на одной странице (например, дашборды).

#### 4.2. Сброс состояний
При закрытии модалок **ОБЯЗАТЕЛЬНО** сбрасывайте связанные состояния, чтобы избежать утечек памяти и показа устаревших данных при следующем открытии:

```tsx
// При закрытии модалки редактирования
const handleEditModalClose = (open: boolean) => {
  setEditModalOpen(open);
  if (!open) {
    setEditingRole(null); // ✅ Очистка объекта
  }
};
```

#### 4.3. Константа `limit`
Переменную `limit` часто не нужно менять через `useState`, если в UI нет выбора "показывать по 20/50/100". В таком случае объявляйте её как `const limit = 10;` прямо в теле компонента или выносите в константы файла.

---

### 5. Чек-лист для разработчика

При создании новой списочной страницы (`XxxPage.tsx`) убедитесь, что объявлены все необходимые состояния:

- [ ] Есть ли `searchInput` и `search`?
- [ ] Есть ли `page` и `limit`?
- [ ] Есть ли `isCreateOpen` для модалки создания?
- [ ] Есть ли `editModalOpen` и `editingXxx` (именно объект, а не ID) для модалки редактирования?
- [ ] Есть ли `deleteXxxId` для `AlertDialog`?
- [ ] Есть ли `highlightedXxxId` для подсветки строки?
- [ ] Сбрасываются ли состояния (например, `editingXxx = null`) при закрытии модалок?

Следование этому правилу делает код всех CRUD-страниц в Cool ERP абсолютно предсказуемым, легко читаемым и готовым к внедрению сложных UX-паттернов (умные тосты, подсветка, пагинация).
