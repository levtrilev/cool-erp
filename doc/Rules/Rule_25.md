# Правило №25: Обязательный `refetch()` после удаления

После успешного удаления записи на любой списочной CRUD-странице **ОБЯЗАТЕЛЬНО** вызывать `await refetch()` для принудительного обновления данных текущей страницы. Это гарантирует корректное отображение актуальных данных, автоматический пересчет пагинации и общего количества записей без необходимости ручной перезагрузки страницы пользователем.

---

### 1. Обоснование (Почему это важно)

Если не обновить данные после удаления:
1. **"Призрачные" записи:** Удаленная строка останется висеть в таблице до следующей перезагрузки страницы или перехода на другой роут.
2. **Сломанная пагинация:** Счетчик "Всего записей" (total) останется прежним, а пагинация будет показывать неверное количество страниц.
3. **Ошибки при переходе:** Если пользователь попытается открыть карточку только что удаленного элемента (например, из истории браузера или по прямой ссылке), он получит ошибку 404.

---

### 2. Обязательные требования к реализации

#### 2.1. Использование `await`
Вызов `refetch()` возвращает Promise. Его **ОБЯЗАТЕЛЬНО** нужно использовать с `await`, чтобы дождаться реального обновления данных от сервера перед показом toast-уведомления или закрытием диалога подтверждения.

#### 2.2. Место вызова
`refetch()` должен вызываться **строго внутри блока `onSuccess`** мутации удаления или сразу после успешного выполнения мутации, но до любых UI-действий (закрытие модалки, показ тоста).

#### 2.3. Запрет на ручное удаление из стейта
**КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** вручную фильтровать массив данных в локальном стейте (например, `setData(prev => prev.filter(item => item.id !== id))`). Это антипаттерн, который ломает пагинацию и кэш TanStack Query. Всегда полагайтесь на серверный `refetch()`.

---

### 3. Примеры кода

#### ✅ ПРАВИЛЬНО: Удаление с `await refetch()`

```tsx
// 1. Инициализация хуков
const queryClient = useQueryClient();
const { toast } = useToast();

// Получаем данные и функцию refetch
const { data, isLoading, refetch } = useReadRolesRolesGet(
  { skip: (page - 1) * limit, limit, search },
  { queryKey: ["roles", page, limit, search] }
);

// Мутация удаления (Orval хук)
const deleteMutation = useDeleteRoleRolesRoleIdDelete();

// 2. Обработчик удаления
const handleDelete = async (roleId: string) => {
  try {
    // ✅ Выполняем удаление
    await deleteMutation.mutateAsync({ role_id: roleId });
    
    // ✅ КРИТИЧЕСКИ ВАЖНО: Ждем обновления данных с сервера
    await refetch(); 
    
    // ✅ Показываем уведомление только после того, как данные обновились
    toast({
      title: "Роль удалена",
      description: "Запись успешно удалена из системы.",
    });
    
    // Сбрасываем ID удаляемой роли (закрываем AlertDialog)
    setDeleteRoleId(null);
    
  } catch (error) {
    toast({
      variant: "destructive",
      title: "Ошибка",
      description: "Не удалось удалить роль. Попробуйте позже.",
    });
  }
};
```

#### ✅ ПРАВИЛЬНО: Альтернатива через `onSuccess` в мутации

Если вы предпочитаете выносить логику в саму мутацию (хотя явный `await refetch()` в обработчике часто предпочтительнее для контроля UI):

```tsx
const deleteMutation = useDeleteRoleRolesRoleIdDelete({
  onSuccess: async () => {
    // ✅ Принудительное обновление текущей страницы
    await refetch(); 
    
    toast({ title: "Успешно удалено" });
    setDeleteRoleId(null);
  },
  onError: () => {
    toast({ variant: "destructive", title: "Ошибка удаления" });
  }
});

const handleDelete = (roleId: string) => {
  deleteMutation.mutate({ role_id: roleId });
};
```

#### ❌ НЕПРАВИЛЬНО: Ручная фильтрация стейта (Антипаттерн)

```tsx
// ❌ ГРУБОЕ НАРУШЕНИЕ ПРАВИЛА №25
const [roles, setRoles] = useState<RoleResponseSchema[]>([]);

const handleDelete = async (roleId: string) => {
  await deleteMutation.mutateAsync({ role_id: roleId });
  
  // ❌ ЗАПРЕЩЕНО: Ручное удаление из массива. 
  // Это не обновит счетчик total, не пересчитает пагинацию и рассинхронизирует кэш.
  setRoles(prev => prev.filter(r => r.id !== roleId)); 
  
  toast({ title: "Удалено" });
};
```

#### ❌ НЕПРАВИЛЬНО: Отсутствие `await`

```tsx
// ❌ ОШИБКА: refetch() вызван, но не ждет завершения.
// Тост покажется мгновенно, но таблица может обновиться на 500мс позже, 
// что создаст неприятный визуальный "скачок" интерфейса.
const handleDelete = async (roleId: string) => {
  await deleteMutation.mutateAsync({ role_id: roleId });
  refetch(); // ❌ Нет await!
  toast({ title: "Удалено" }); 
};
```

---

### 4. Нюанс: Удаление последнего элемента на странице

Если пользователь удаляет **последнюю запись на текущей странице** (и это не первая страница), после `refetch()` таблица станет пустой, а пагинация все еще будет показывать текущий номер страницы. 

Чтобы улучшить UX, можно добавить небольшую проверку после `refetch()`:

```tsx
const handleDelete = async (roleId: string) => {
  await deleteMutation.mutateAsync({ role_id: roleId });
  await refetch();
  
  // ✅ Умная пагинация: если страница опустела и мы не на первой странице — переходим назад
  if (data?.data?.items.length === 0 && page > 1) {
    setPage(prev => prev - 1);
  }
  
  setDeleteRoleId(null);
  toast({ title: "Роль удалена" });
};
```
*(Примечание: Это расширение базового правила, но оно настоятельно рекомендуется для идеального UX).*

---

### 5. Чек-лист для разработчика

При реализации кнопки удаления на любой CRUD-странице:
- [ ] Используется ли `await refetch()` после успешного вызова мутации?
- [ ] Отсутствует ли ручное изменение массива данных (`setData`, `filter`, `splice`)?
- [ ] Показывается ли toast-уведомление **после** (а не до или одновременно) завершения `refetch()`?
- [ ] Закрывается ли диалог подтверждения (`AlertDialog`) только после успешного обновления данных?

Следование этому правилу гарантирует, что интерфейс списка всегда будет находиться в строгом соответствии с состоянием базы данных.
