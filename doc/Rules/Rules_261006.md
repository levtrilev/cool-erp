Вот полное, структурированное и актуальное изложение всех правил проекта **Cool ERP**, сформированных и уточненных в ходе нашей работы. Этот документ служит единым источником истины (Single Source of Truth) для разработки.

# 📜 Свод правил проекта Cool ERP (v1.0)

## 🏛️ ЧАСТЬ 1: АРХИТЕКТУРА И BACKEND

### Правило №1: Чистая архитектура и ORM
* Вычисляемые поля в SQLAlchemy-моделях **обязательно** реализуются через `@property`.
* Отношения (`relationship`) должны использовать `back_populates` и `lazy="selectin"` для предотвращения N+1 запросов.
* Pydantic-схемы для ответов должны иметь `model_config = ConfigDict(from_attributes=True)` для автоматического чтения `@property` из ORM-объектов.

### Правило №4: Orval-совместимость API
* Все эндпоинты, возвращающие списки, **обязаны** использовать единую обёртку ответа: `ApiResponse[PaginatedResponse[T]]`.
* Это гарантирует корректную генерацию TypeScript-типов на фронтенде через Orval.

### Правило №21: Именование схем (Суффиксы)
* Схемы Pydantic должны иметь четкие суффиксы: `CreateSchema`, `UpdateSchema`, `ResponseSchema`.

### Правило №26: Безопасность Multi-tenancy
* Обычные пользователи видят **только** данные своего `tenant_id`.
* Фильтрация по `tenant_id` реализуется на уровне SQL-запроса в CRUD-методах. Суперадмины видят все данные.

### Правило №28: Явность схемы БД и ограничений
* В `__table_args__` моделей SQLAlchemy явно указывается схема `{"schema": "public"}`.
* Ограничения уникальности (`UniqueConstraint`) должны иметь явные имена (например, `uq_domains_name`).

### Правило №30: Синхронизация M2M связей
* Связи многие-ко-многим (например, `tenant_ids`) не являются колонками таблицы. Их синхронизация (вставка/удаление через `insert`/`delete`) **обязательно** реализуется в переопределенных методах `create` и `update` CRUD-класса.

### Правило №31: Приоритет базового класса `CRUDBase`
* Все CRUD-классы **обязаны** наследоваться от `CRUDBase[Model, CreateSchema, UpdateSchema]`.
* Переопределение методов (`create`, `update`, `get_multi_paginated`, `remove`) допускается **только** при наличии специфичной бизнес-логики (M2M, уникальность, защита от удаления).
* При переопределении **строго запрещено** менять имена параметров базового класса. Используйте: `obj_in`, `db_obj`, `user_is_superadmin`.

### Правило №32: Аннотированные типы для безопасности
* Использование `Depends(...)` в значениях по умолчанию параметров роутеров **запрещено**.
* **Обязательно** использовать алиасы `Annotated`: `SuperAdminUser`, `CurrentUser`, `DBSession`, определенные в `dependencies.py`.

### Правило №33: Запрет присваивания в `@property`
* Поля, объявленные как `@property` в ORM-моделях, являются **read-only**.
* Присваивание значений этим полям (например, `item.tenant_ids = [...]`) в CRUD-методах **категорически запрещено**. Значение должно вычисляться автоматически.

## 💻 ЧАСТЬ 2: FRONTEND И UI/UX

### Правило №11: Компактность таблиц
* Ячейки таблиц должны иметь минимальные вертикальные отступы (`py-1`), текст должен быть выровнен по верхнему краю (`align-top`).

### Правило №12: Поиск через форму
* Поле поиска должно быть обернуто в `<form onSubmit={...}>`. Активация поиска происходит по нажатию Enter или кнопки, а не на каждое нажатие клавиши (`onChange` обновляет только локальный стейт `searchInput`).

### Правило №13 и №14: Структура таблицы
* Использование `table-fixed` для предсказуемой ширины.
* Длинный текст в ячейках должен обрезаться с многоточием (`truncate`) и иметь `title` для показа полного текста при наведении.

### Правило №16: Подтверждение деструктивных действий
* Удаление любых сущностей **обязательно** должно подтверждаться через компонент `AlertDialog`.

### Правило №17, №18, №23: Умная навигация и подсветка
* После сохранения новой или измененной записи строка в таблице должна подсвечиваться (через `useEffect` и стейт `highlightedId`).
* Если запись оказалась на другой странице, пользователю должно быть предложено перейти на эту страницу, либо переход должен выполняться автоматически.

### Правило №20: Управление состоянием модалок
* Модалки должны проверяться на `null` перед открытием.
* При закрытии модалки состояние формы **обязательно** сбрасывается в исходное (через `reset(CREATE_DEFAULTS)`).

### Правило №22: Структура состояний
* Состояние поиска должно быть разделено: `searchInput` (то, что печатает пользователь) и `search` (то, что передается в API при сабмите формы).

### Правило №29: Изменяемая ширина колонок
* Таблицы должны поддерживать ручное изменение ширины колонок пользователем через хук `useResizableColumns`.

### Правило №34: Стандартный паттерн Switch (Переключатель)
* Переключатели в формах **обязательно** реализуются через `Controller` из `react-hook-form`.
* Прямая привязка: `checked={field.value}` и `onCheckedChange={field.onChange}` (без `!!`, `??` или `Boolean()`, если `defaultValues` настроены верно).
* Рядом с `Switch` должен быть `Label` с `htmlFor`, меняющий цвет и иконку (`CheckCircle2` / `PauseCircle`) в зависимости от состояния.
* Использование `useState` для управления переключателем внутри формы запрещено.

## 🔗 ЧАСТЬ 3: ИНТЕГРАЦИЯ И ТИПИЗАЦИЯ

### Правило №24: Инвалидация кэша
* Вызов `queryClient.invalidateQueries` должен выполняться **ДО** закрытия модального окна успешного сохранения, чтобы таблица обновилась бесшовно.

### Правило №25: Обновление после удаления
* После успешного вызова мутации удаления **обязательно** вызывать `refetch()` для актуализации списка на текущей странице.

### Правило №27: Использование `ReferenceSelect` для справочников
* Ручной ввод UUID через `<Input>` или использование стандартного `<select>` **запрещено**.
* Используется компонент `<ReferenceSelect>`.
* **Обязательный паттерн адаптера:** Поскольку Orval возвращает `ApiResponse<PaginatedResponse<T>>`, а компонент ожидает `{ items, total }`, в пропсе `fetchFn` **обязательно** используется функция-адаптер:
  ```tsx
  fetchFn={async (params) => {
    const response = await getXxxXxxGet(params);
    return {
      items: response?.data?.items ?? [],
      total: response?.data?.total ?? 0,
    };
  }}
  ```
* Изменение кода самого файла `ReferenceSelect.tsx` для обхода типизации **запрещено**.
* Для дополнительных колонок используется массив `columns` с ключом **`column`** (не `key` и не `labelField`).

## 💡 ДОПОЛНИТЕЛЬНЫЕ ЛУЧШИЕ ПРАКТИКИ (Best Practices)

1. **Константы для сброса форм:** Для гарантированного сброса формы в чистое состояние (особенно для массивов вроде `tenant_ids: []`) используйте вынесенную константу `CREATE_DEFAULTS`, которая передается и в `useForm({ defaultValues: CREATE_DEFAULTS })`, и в `reset(CREATE_DEFAULTS)` при закрытии модалки.
2. **Централизованная обработка ошибок БД:** Используйте декоратор `@with_db_error_handling` в базовом `CRUDBase` для автоматического `rollback`, логирования и преобразования сырых ошибок SQLAlchemy (например, `IntegrityError`) в понятные `HTTPException(400)`.
3. **Cookie-based авторизация:** При кросс-доменных запросах (localhost:5173 → localhost:8000) Axios-клиент **обязан** иметь настройку `withCredentials: true`, а бэкенд должен устанавливать Cookie с флагом `samesite="lax"` и `secure=False` (для локальной разработки).

---

Этот свод правил обеспечивает строгую типобезопасность, единообразие кода, защищенность от типичных ошибок и высокую производительность как на бэкенде, так и на фронтенде. Любое отступление от этих правил должно быть явно обосновано.
