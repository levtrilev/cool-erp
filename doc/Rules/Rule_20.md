# Правило №20: Модальные компоненты редактирования

Все модальные компоненты, предназначенные для редактирования или просмотра конкретной сущности, **ОБЯЗАТЕЛЬНО** должны иметь проверку на `null` через условный рендеринг и уникальный проп `key` для принудительного перемонтирования при смене сущности.

**СТРОГИЕ ТРЕБОВАНИЯ:**
1. Обёртка условного рендеринга: `{editingXxx && (...)}`
2. Уникальный ключ: `key={editingXxx.id}`

---

### 1. Обоснование (Почему это важно)

1. **Изоляция состояния формы:** Если использовать просто `<Modal open={!!editingRole} />`, React не размонтирует компонент при закрытии. При открытии следующей сущности форма (например, React Hook Form) может сохранить значения от предыдущей записи, что приведет к отправке устаревших данных.
2. **Предотвращение утечек памяти и фоновых запросов:** Условный рендеринг (`&&`) полностью уничтожает компонент из DOM при закрытии, отменяя все его внутренние `useEffect`, таймеры и подписки.
3. **Защита от ошибок рендеринга:** Если передать `null` в пропсы модалки, а внутри неё обратиться к `editingXxx.name`, приложение упадет с ошибкой `Cannot read properties of null`.

---

### 2. Обязательные требования к реализации

#### 2.1. Условный рендеринг (Null-check)
Модалка не должна рендериться, если сущность для редактирования не выбрана (`null` или `undefined`).

#### 2.2. Проп `key` для перемонтирования
При открытии модалки для редактирования **разных** записей, React должен полностью уничтожить старый экземпляр компонента и создать новый. Это гарантирует сброс всех внутренних состояний (инпутов, флагов загрузки, локальных стейтов).

#### 2.3. Обработка закрытия (`onOpenChange`)
Родительский компонент должен корректно обрабатывать закрытие модалки, сбрасывая объект редактируемой сущности в `null`.

---

### 3. Примеры кода

#### ✅ ПРАВИЛЬНО: Родительская страница (`RolesPage.tsx`)

```tsx
import { EditRoleModal } from "./EditRoleModal";

export const RolesPage = () => {
  const [editModalOpen, setEditModalOpen] = useState(false);
  const [editingRole, setEditingRole] = useState<RoleResponseSchema | null>(null);

  // Обработчик открытия
  const handleEdit = (role: RoleResponseSchema) => {
    setEditingRole(role);
    setEditModalOpen(true);
  };

  // Обработчик закрытия
  const handleEditModalClose = (open: boolean) => {
    setEditModalOpen(open);
    if (!open) {
      // ✅ Сбрасываем объект при закрытии
      setEditingRole(null); 
    }
  };

  return (
    <div>
      {/* ... таблица и кнопки ... */}

      {/* ✅ ПРАВИЛЬНЫЙ ВЫЗОВ МОДАЛКИ */}
      {editingRole && (
        <EditRoleModal
          key={editingRole.id} // ✅ КРИТИЧЕСКИ ВАЖНО: Принудительное перемонтирование
          open={editModalOpen}
          onOpenChange={handleEditModalClose}
          role={editingRole}
          onRoleSaved={handleRoleSaved}
        />
      )}
    </div>
  );
};
```

#### ❌ НЕПРАВИЛЬНО: Использование без `key` и без условного рендеринга

```tsx
// ❌ ОШИБКА 1: Отсутствие key.
// При переходе от Роли А к Роли Б форма не сбросится, React Hook Form 
// может показать старые данные или выдать предупреждения о смене controlled/uncontrolled.
<EditRoleModal
  open={editModalOpen}
  onOpenChange={setEditModalOpen}
  role={editingRole} 
/>

//  ОШИБКА 2: Отсутствие проверки на null.
// Если editingRole === null, модалка попытается отрендериться с role={null}, 
// что вызовет краш внутри компонента при обращении к role.name.
<EditRoleModal
  open={!!editingRole} 
  onOpenChange={(open) => { if (!open) setEditingRole(null); }}
  role={editingRole}
/>
```

### 4. Нюансы и лучшие практики

#### 4.1. Модалка создания (Create) vs Редактирования (Edit)
Для модалки **создания** `key` не нужен, так как там нет редактируемой сущности, но условный рендеринг допустим (хотя для создания часто используют просто `open={isCreateOpen}`, так как начальное состояние формы всегда пустое).

```tsx
// Для создания ключ не обязателен, но условный рендеринг приветствуется
{isCreateOpen && (
  <CreateRoleModal
    open={isCreateOpen}
    onOpenChange={setIsCreateOpen}
    onRoleCreated={handleRoleCreated}
  />
)}
```

#### 4.2. Внутренняя логика модалки
Внутри самой модалки (`EditRoleModal.tsx`) проп `role` должен быть типизирован как **обязательный** (не nullable), так как мы гарантировали его наличие через `{editingRole && ...}` на уровне родителя:

```tsx
interface EditRoleModalProps {
  open: boolean;
  onOpenChange: (open: boolean) => void;
  role: RoleResponseSchema; // ✅ НЕ nullable! Родитель уже проверил на null.
  onRoleSaved: (id: string, name: string) => void;
}
```

#### 4.3. Сброс состояния при закрытии
Никогда не полагайтесь на то, что пользователь нажмет "Отмена". Закрытие по крестику (X), клику вне окна или нажатию Escape должно гарантированно вызывать `onOpenChange(false)`, который в родителе сбросит `editingXxx` в `null`.

---

### 5. Чек-лист для разработчика

При реализации или рефакторинге модальных окон редактирования проверьте:

- [ ] Используется ли условный рендеринг `{editingXxx && <Modal ... />}` на уровне родителя?
- [ ] Передан ли проп `key={editingXxx.id}` в компонент модалки?
- [ ] Типизирован ли проп `role` (или `item`) внутри модалки как **обязательный** (без `| null`)?
- [ ] Сбрасывается ли состояние `editingXxx` в `null` при вызове `onOpenChange(false)`?
- [ ] Отсутствует ли внутри модалки логика типа `if (!role) return null` (эта проверка уже сделана родителем)?

Следование этому правилу гарантирует, что формы редактирования всегда будут находиться в чистом, предсказуемом состоянии, а приложение будет защищено от ошибок рендеринга при работе с пустыми данными.
