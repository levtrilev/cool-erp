# Правило №24: Обязательный вызов `invalidateQueries` в модалке

Каждая модалка создания или редактирования **ОБЯЗАТЕЛЬНО** должна инвалидировать кэш TanStack Query **ДО** закрытия самой модалки и **ДО** вызова callback-ов родительской страницы. 

**СТРОГИЙ ПОРЯДОК ДЕЙСТВИЙ:**
1. `invalidateQueries` (помечаем кэш устаревшим и запускаем фоновое обновление)
2. `onOpenChange(false)` (закрываем модалку)
3. `await onXxxUpdated(...)` (уведомляем родителя)

---

### 1. Обоснование (Почему важен именно этот порядок)

Нарушение последовательности приводит к трем типичным багам:
1. **Stale Data (Устаревшие данные):** Если сначала вызвать callback родителя, родительская страница может попытаться найти новую запись в кэше, который еще не обновился.
2. **Race Conditions (Гонка состояний):** Если сначала закрыть модалку (`onOpenChange(false)`), React размонтирует компонент. Фоновые запросы, инициированные инвадацией, могут быть отменены браузером или вызвать предупреждения об утечках памяти в консоли React.
3. **Визуальные артефакты:** Подсветка новой строки или toast-уведомление могут сработать до того, как таблица физически перерисуется с новыми данными.

---

### 2. Обязательные требования к реализации

#### 2.1. Инвалидация кэша
Используйте `queryClient.invalidateQueries` с правильным `queryKey`, который использует родительская страница для получения списка.

#### 2.2. Асинхронность
Операции должны выполняться последовательно. Если родительский callback (`onEntitySaved`) содержит асинхронную логику (например, навигацию или поиск по полному списку), его **ОБЯЗАТЕЛЬНО** нужно вызывать с `await`.

#### 2.3. Обработка ошибок
Весь блок должен быть обернут в `try/catch`. Если мутация на сервере упала, модалка **НЕ должна** закрываться, а кэш не должен инвалидироваться.

---

### 3. Примеры кода

#### ✅ ПРАВИЛЬНО: Строгое соблюдение последовательности

```tsx
import { useQueryClient } from "@tanstack/react-query";
import { useCreateRoleRolesPost } from "@/api/generated/roles/roles";

export function CreateRoleModal({ open, onOpenChange, onRoleSaved }) {
  const queryClient = useQueryClient();
  const { toast } = useToast();
  
  // Orval хук мутации
  const createMutation = useCreateRoleRolesPost();

  const onSubmit = async (data: RoleFormData) => {
    try {
      // 1. Отправляем данные на сервер
      const response = await createMutation.mutateAsync({ data });
      const newRole = response.data;

      // ✅ ШАГ 1: Инвалидируем кэш списка ролей
      // Это запускает фоновый refetch на родительской странице
      await queryClient.invalidateQueries({ queryKey: ["roles"] });

      // ✅ ШАГ 2: Закрываем модалку
      // Делаем это после инвалидации, чтобы React не прервал фоновые запросы
      onOpenChange(false);

      // ✅ ШАГ 3: Уведомляем родителя (передаем ID и имя для подсветки/навигации)
      // Используем await, чтобы дождаться завершения логики родителя
      await onRoleSaved(newRole.id, newRole.name);

      toast({ title: "Роль успешно создана" });
      
    } catch (error) {
      // ❌ При ошибке модалка НЕ закрывается, кэш НЕ инвалидируется
      toast({
        variant: "destructive",
        title: "Ошибка",
        description: "Не удалось сохранить роль",
      });
    }
  };

  // ... JSX формы
}
```

#### ✅ ПРАВИЛЬНО: Для режима редактирования (Update)

```tsx
  const onSubmit = async (data: RoleFormData) => {
    try {
      await updateMutation.mutateAsync({ role_id: role.id, data });

      // ✅ Та же строгая последовательность
      await queryClient.invalidateQueries({ queryKey: ["roles"] });
      onOpenChange(false);
      await onRoleUpdated(role.id, data.name);
      
      toast({ title: "Роль обновлена" });
    } catch (error) {
      // Обработка ошибок
    }
  };
```

#### ❌ НЕПРАВИЛЬНО: Неправильный порядок (Закрытие модалки первым)

```tsx
// ❌ ОШИБКА: Сначала закрываем модалку
onOpenChange(false); 

// ❌ ОШИБКА: Потом инвалидируем кэш
await queryClient.invalidateQueries({ queryKey: ["roles"] });

// ❌ ОШИБКА: Родитель может не успеть получить свежие данные
await onRoleSaved(newRole.id, newRole.name); 
```
*Почему это плохо:* React начинает процесс размонтирования модалки. Если `invalidateQueries` инициирует запросы, которые зависят от контекста модалки (или если пользователь быстро откроет другую модалку), это может привести к непредсказуемому поведению UI.

#### ❌ НЕПРАВИЛЬНО: Отсутствие `invalidateQueries` (Надежда на родителя)

```tsx
// ❌ ОШИБКА: Модалка просто закрывается и дергает родителя
onOpenChange(false);
await onRoleSaved(newRole.id, newRole.name);
```
*Почему это плохо:* Родительская страница (`RolesPage`) может использовать `refetch()` в своем callback'е, но это создает жесткую зависимость. Модалка должна сама гарантировать, что глобальный кэш TanStack Query помечен как `stale` (устаревший), чтобы любые другие компоненты, использующие этот кэш, тоже обновились.

---

### 4. Нюанс: Оптимистичные обновления (Optimistic Updates)

Если вы используете оптимистичные обновления в TanStack Query (мгновенное обновление UI до ответа сервера), правило №24 всё равно остается в силе. `invalidateQueries` в данном случае служит "предохранителем", который сверяет оптимистично добавленные данные с реальным ответом сервера и откатывает их в случае ошибки.

---

### 5. Чек-лист для разработчика

При написании обработчика `onSubmit` в любой модалке (Create/Edit) проверьте:

- [ ] Есть ли вызов `queryClient.invalidateQueries({ queryKey: [...] })`?
- [ ] Вызывается ли `invalidateQueries` **строго до** `onOpenChange(false)`?
- [ ] Вызывается ли `onOpenChange(false)` **строго до** callback'а родителя (`onXxxSaved`)?
- [ ] Используется ли `await` перед callback'ом родителя?
- [ ] Находятся ли все три шага внутри блока `try` (после успешной мутации)?
- [ ] Закрыта ли модалка в блоке `catch`? (Ответ: **НЕТ**, она должна оставаться открытой при ошибке).

Следование этому правилу гарантирует идеальную синхронизацию состояния между модалками, родительскими страницами и глобальным кэшем TanStack Query.
