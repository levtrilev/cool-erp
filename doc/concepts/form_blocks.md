# Архитектура сложных форм: композиция строительных блоков, а не рантайм-метаданные

## Прямой ответ на ваш вопрос

Это **не чистые бизнес-метаданные** (декларативный конфиг, интерпретируемый универсальным рендерером в рантайме) и **не «просто разметка»** (императивный JSX без абстракций). Правильный ответ — **композиция типизированных строительных блоков в компонентах вкладок**, где:

| Аспект | Где определён | Форма |
|---|---|---|
| **Структура вкладок** (какие вкладки, что в какой) | Разметка в компоненте модалки | Императивный JSX |
| **Расположение секций** (поля сверху, таблицы снизу) | Разметка в компоненте вкладки | Императивный JSX |
| **Описания полей** (метка, тип, валидация) | Типизированные константы | `const` в `config.ts` / `schemas.ts` |
| **Описания колонок таблиц** (ключ, метка, ширина) | Типизированные константы | `const` в `config.ts` |
| **Логика черновиков таблиц** | Отдельные компоненты | Контейнерные компоненты |

Ключевой принцип: **`form_generation_v1.2.md` — это формат задания для генерации кода, а НЕ рантайм-конфиг.** Спецификация описывает, какой код сгенерировать, но сгенерированный код — обычные компоненты, использующие строительные блоки. Никакого динамического рендеринга по строковым ключам в рантайме.

## Диаграмма композиции: где какая часть формы

```
EditSalesOrderModal
│
├── useDocumentSave<SalesOrderFormData>      ← логика сохранения (каркас)
│
└── <DocumentFormShell>                       ← обёртка: заголовок, типовые поля, футер
    │
    └── children:
        └── <FormTabs>                        ← СЛОЙ 2: строительный блок вкладок
            │
            ├── <FormTabPanel value="main" label="Основное">
            │   └── <SalesOrderMainTab>       ← СЛОЙ 3: бизнес-компонент вкладки
            │       │
            │       ├── ВЕРХНЯЯ ПОЛОВИНА (простая часть — поля записи БД):
            │       │   └── <FieldsGrid cols={2}>
            │       │       ├── <FieldBlock name="client_id" label="Клиент" />
            │       │       ├── <FieldBlock name="region_id" label="Регион" />
            │       │       ├── <FieldBlock name="contract_id" label="Договор" />
            │       │       └── ... (много полей в 2 колонки)
            │       │
            │       └── НИЖНЯЯ ПОЛОВИНА (две табличные части):
            │           ├── <TableSection title="Строки заказа">
            │           │   └── <OrderLinesTable />      ← табличная часть 1
            │           │
            │           └── <TableSection title="Входящие партии">
            │               └── <IncomingBatchesTable /> ← табличная часть 2
            │
            └── <FormTabPanel value="payments" label="Оплаты">
                └── <SalesOrderPaymentsTab>   ← СЛОЙ 3: бизнес-компонент вкладки
                    │
                    ├── ВЕРХНЯЯ ПОЛОВИНА (поля оплат):
                    │   └── <FieldsGrid cols={2}>
                    │       ├── <FieldBlock name="currency" label="Валюта" />
                    │       ├── <FieldBlock name="payment_scheme" label="Схема оплаты" />
                    │       └── <ReadOnlyGroup label="Суммы">
                    │           ├── <ReadonlyField name="total_amount" />
                    │           ├── <ReadonlyField name="paid_amount" />
                    │           └── <ReadonlyField name="overdue_info" />
                    │
                    └── НИЖНЯЯ ПОЛОВИНА (табличная часть 3):
                        └── <TableSection title="Платежи">
                            └── <PaymentsTable />         ← таблица платежей
```

**Принцип:** каждая часть формы — отдельный компонент. Вкладка содержит поля и таблицы. Таблица — самостоятельный компонент с черновиком. Поля группируются в сетки. Всё это композиция строительных блоков.

## Где метаданные, а где разметка

| Элемент | Тип | Пример | Где живёт |
|---|---|---|---|
| Вкладки («Основное», «Оплаты») | **Разметка** | `<FormTabs>` + `<FormTabPanel>` | `EditSalesOrderModal.tsx` |
| Расположение полей (2 колонки, сверху) | **Разметка** | `<FieldsGrid cols={2}>` | `SalesOrderMainTab.tsx` |
| Расположение таблиц (одна над другой) | **Разметка** | `<TableSection>` последовательно | `SalesOrderMainTab.tsx` |
| Метки и плейсхолдеры полей | **Константы** | `label="Клиент"`, `placeholder="Выберите клиента"` | в `FieldBlock` или в `config.ts` |
| Колонки таблиц | **Константы** | `ORDER_LINES_COLUMNS: ColumnDef[]` | `config.ts` |
| Zod-схема валидации | **Константа** | `salesOrderSchema = z.object({...})` | `schemas.ts` |
| Дефолты формы | **Константа** | `CREATE_DEFAULTS` | `schemas.ts` |
| Логика черновика таблицы | **Компонент** | `useState` + `useRef` + `useEffect` | `OrderLinesTable.tsx` |

**Константы** (`config.ts`, `schemas.ts`) — это **типизированные описания**, используемые компонентами напрямую. Они НЕ интерпретируются универсальным рендерером. Это даёт строгую типизацию и простую отладку.

## Почему не чистые метаданные (декларативный рантайм-рендерер)

| Критерий | Чистые метаданные | Композиция блоков |
|---|---|---|
| Типизация | ❌ Динамический рендеринг по строковым ключам → потеря типов, `any` | ✅ Строгая типизация через дженерики |
| Таблицы с черновиками | ❌ Очень сложно описать декларативно | ✅ Отдельные компоненты с полной логикой |
| Вложенные таблицы (партии для строк) | ❌ Практически невозможно | ✅ Композиция компонентов |
| Нестандартные элементы | ❌ Требуют «escape hatch» | ✅ Любая гибкость |
| Отладка | ❌ Сложно (рендерер скрыт) | ✅ Обычный брейкпоинт в компоненте |
| Соответствие Правилу №44 | ❌ Невозможно без кастов | ✅ Полное |

Табличные части вашего примера (строки заказа, партии для строк, платежи) — это сложные компоненты с черновиками, связями между таблицами, добавлением/удалением строк. Декларативный рендерер не справится с этим без потери типобезопасности или без огромного числа «кастомных слотов», что сводит на нет преимущества декларативности.

## Почему не «просто разметка» (без строительных блоков)

| Критерий | Просто разметка | Композиция блоков |
|---|---|---|
| Дублирование | ❌ Каждая форма заново пишет сетки, обёртки, вкладки | ✅ Строительные блоки переиспользуются |
| Единообразие | ❌ Зависит от дисциплины разработчика | ✅ Гарантировано блоками |
| Поддержка | ❌ Изменение стиля — правка каждой формы | ✅ Изменение блока → все формы |
| Соответствие Правилам №41, №46 | ⚠️ Требует ручной дисциплины | ✅ Встроено в блоки |

## Управление состоянием табличных частей (Правило №46)

Каждая табличная часть — **отдельный компонент с собственным черновиком**. Это критично для сложных форм:

```
Тип состояния        Где хранится              Кто управляет
─────────────────────────────────────────────────────────────────
Серверные данные     React Query               Orval-хуки
Поля формы           react-hook-form           useForm в модалке
Черновик таблицы     useState в компоненте     Компонент таблицы
```

Таблица строк заказа (`OrderLinesTable`) имеет:
- `useState<LineDraft[]>([])` — черновик строк.
- `useRef<string | null>(null)` — защита от повторной инициализации.
- `useEffect` — инициализация после загрузки данных (Правило №38).
- Флаги `markedForDeletion` для пометки на удаление.
- Передаёт изменения вверх через `onChange(drafts)` или через `useMemo`-индикатор.

Это **не поле формы** (не управляется через `useForm`), а **самостоятельный компонент** с локальным состоянием. Строительный блок `TableSection` обеспечивает только внешний вид (заголовок, обёртка), а логика черновика — в самом компоненте таблицы.

## Связь с `form_generation_v1.2.md`

Спецификация `cool-erp-form` используется для **декларативной генерации кода**, а не для рантайм-интерпретации:

```
ЗАДАНИЕ (cool-erp-form v1.2)
        │
        │  [генерация кода ИИ или скриптом]
        ▼
СГЕНЕРИРОВАННЫЙ КОД:
  • EditSalesOrderModal.tsx  (композиция каркаса и вкладок)
  • SalesOrderMainTab.tsx    (композиция строительных блоков)
  • OrderLinesTable.tsx      (компонент с черновиком)
  • schemas.ts, config.ts    (типизированные константы)
        │
        │  [использует]
        ▼
СТРОИТЕЛЬНЫЕ БЛОКИ + КАРКАС (уже существуют)
```

То есть `form_generation_v1.2.md` описывает **ЧТО** сгенерировать, а сгенерированный код использует строительные блоки для **КАК**. Никакого рантайм-рендеринга по спецификации.

## Рекомендуемые следующие шаги

Прежде чем массово создавать бизнес-сущности, создайте **Слой 2 — строительные блоки**. Это фундамент, без которого каждая форма будет дублировать код.

### Шаг 1. Создать `src/lib/form-blocks/` с минимальным набором

| Блок | Назначение | Приоритет |
|---|---|---|
| `FormTabs` / `FormTabPanel` | Вкладки с индикаторами изменений | Высокий |
| `FieldsGrid` | Сетка полей (2 колонки) | Высокий |
| `FieldBlock` | Одно поле (метка + контроллер + ошибка) | Высокий |
| `TableSection` | Обёртка таблицы с заголовком | Высокий |
| `ReadOnlyGroup` / `ReadonlyField` | Группа полей только для чтения | Средний |
| `FormSection` | Именованная секция с разделителем | Средний |

### Шаг 2. Пилотная сложная форма

Возьмите один реальный документный модуль (например, будущий `sales/orders` или другой с табличными частями) и реализуйте его по этой архитектуре. Это выявит пробелы в строительных блоках до массового тиражирования.

### Шаг 3. Документировать паттерн

После пилота зафиксируйте паттерн как **Правило №48** (или расширение Правила №46): «Архитектура сложных документных форм». Это обеспечит единообразие при массовом создании сущностей.

### Шаг 4. Массовое тиражирование

С готовыми строительными блоками и задокументированным паттерном каждая новая документная форма создаётся по единому шаблону: каркас + вкладки + поля + таблицы. Можно использовать `form_generation_v1.2.md` как формат задания для генерации кода.

## Итог

Части формы документа (простая и табличные) и их оформление в виде вкладок — это **композиция типизированных строительных блоков в компонентах вкладок**, а не рантайм-метаданные. Структура вкладок и расположение секций задаётся разметкой в компоненте, описания полей и колонок — типизированными константами, а логика табличных черновиков — отдельными компонентами по Правилу №46. Такой подход сохраняет строгую типизацию, обеспечивает единообразие через переиспользуемые блоки и даёт гибкость для сложных случаев (вложенные таблицы, черновики, связи между частями), что критично перед массовым созданием бизнес-сущностей.

Готов приступить к проектированию и реализации **Слоя 2 — строительных блоков**, если вы подтверждаете эту архитектуру. Начать рекомендую с `FormTabs`, `FieldsGrid`, `FieldBlock`, `TableSection` — минимального набора, покрывающего ваш пример формы заказа продажи.
