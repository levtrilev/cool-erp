## Область доступа vs Пространства доступа

Область доступа конкретного пользователя складывается следующим образом: Каждая единица информации помещается в некоторое отдельное пространство доступа (Раздел). Пользователю так или иначе формируется набор пространств (сумма Разделов) (каждое целиком или частично - под фильтром), сумма которых и и является областью доступа данного пользователя в данный момент.  

# Пространства доступа - Разделы

**Общее** - фиксированное на уровне платформы, доступное любому пользователю из любой Организации (tenant) общее пространство (Раздел - section name = "Общий" или "Сommon")

**Общее для организации** - создается автоматически при создании Организации (tenant). Фиксированное не может быть удалено, доступное любому пользователю "этой" Организации (Раздел - section name = "Общий" или "Сommon" + "-" + <tenant_name>)

**Обычный раздел** - произвольный раздел внутри одной Организации - произвольное название. Создается Админом Организации. Админ НЕ предоставляет Пользователям своей Организации Права на полный доступ к содержимому Раздела, но предоставляет дифференцированный по уровням доступа (полный/автор/редактор/читатель/удаление) и по типу содержимого (типы документов) путем включения Пользователя в Роль(группу). 

# Область доступа - Роль (сумма Ролей Пользователя)

Каждая единица информации (документ определенного типа) помещена в свой Раздел. Роль является набором параметров, дополнительно ограничивающих доступ Пользователя. Роль описывает:
- Разделы
- Типы документов (для каждого - уровень доступа - (полный/автор/редактор/читатель/удаление))
- Пользователи

# Дополнительное ограничение доступа - RLS на основе Тэгов

Общеизвестна задача разграничения доступа в зависимости от тех или иных значений доменных величин (данных предметной области). Например, сделки с клиентом из определенного региона должны быть доступны только своему региональному менеджеру. Чтобы не "городить" отдельные Разделы для сделок каждого региона (и не решать отдельную сложную задачу переопределения регионов имеющих историю или переназначения региональных менеджеров) попробуем изобрести что-то более элегантное на основе тэгов. Например: у Пользователя есть набор тэгов доступа для типа документа. В каждом экземпляре документа указаны тэги. Voila: Если тэг есть у пользователя и в документе - доступ предоставляется (в соответствии с Ролью)
Необходимо решить такие вопросы:
- AND/OR/NO Tags. Иногда доступ удобнее ограничить по принципу белого списка, иногда по принципу черного списка. Не хочется иметь отдельные поля для Тэгов whiteListTags и BlackListTags.. Одним из вариантов является иметь одно поле Тэгов Tags и плюс переключатель типа TagsAreBlackList.
- Кто может/должен устанавливать Тэги? Вручную или по событиям?
- Кто может видеть установленные Тэги? 


# Критический анализ концепции разграничения доступа

## 1. Краткое резюме концепции

| Слой | Что представляет | Как работает |
|------|------------------|--------------|
| **Разделы** | Пространства доступа (контейнеры) | Фиксированные (платформа, организация) + произвольные (Админ) |
| **Роль** | Набор параметров ограничения | Сумма Разделов × Типов документов × Уровней доступа |
| **Теги** | Дополнительное ограничение (по сути — RLS) | AND/OR/NOT по тегам пользователя и документа |
| **Область доступа** | Пересечение всех слоёв | Сумма Ролей Пользователя, ограниченная Разделами, Типами, Тегами |

Концепция в целом **рабочая** и уже частично воплощена в вашем коде (`PermissionModel` содержит `or_tags`, `and_tags`, `no_tags`, `access_by_tags`, `full_access`, `author`, `reader`, `editor`, `can_delete`). Однако есть ряд архитектурных и логических рисков.

---

## 2. Критический анализ

### ✅ Сильные стороны

1. **Трёхуровневая модель** (Раздел → Роль → Теги) — хорошая декомпозиция, позволяет разделить физическую организацию данных (Разделы) от логических прав (Роли) и контекстных ограничений (Теги).

2. **Разделы «Общее» и «Общее для организации»** — автоматическое создание при создании тенанта снимает рутинную работу с Админа.

3. **Теги с разделением на AND / OR / NOT** — гибкая модель, покрывающая и белый список, и чёрный список, и комбинированные сценарии. В вашем `PermissionModel` это уже реализовано через `or_tags`, `and_tags`, `no_tags`.

4. **Уровни доступа** (полный/автор/редактор/читатель/удаление) — покрывают базовые сценарии работы с документами.

### ⚠️ Слабые стороны и риски

#### А. Разделы: смешение физической организации и логического доступа

**Проблема:** Раздел одновременно является:
- Физическим контейнером («папка», где лежит документ)
- Механизмом контроля доступа (к чему есть доступ)

Это **нарушает принцип единственной ответственности (SRP)**. Если Админ хочет переместить документ из одного раздела в другой для удобства организации, это автоматически меняет область доступа всех пользователей. И наоборот: если нужно изменить права доступа, Админ вынужден создавать новый Раздел или перемещать документы.

**Риск:** Лавинообразное создание Разделов для каждого сочетания прав. Например: «Сделки Центр», «Сделки Сибирь», «Сделки Дальний Восток» — каждый Раздел только для того, чтобы ограничить региональных менеджеров.

**Рекомендация:** Разделить на два понятия:
- **Папка / Категория** — физическая организация данных (может быть иерархической, не влияет на доступ)
- **Пространство доступа (Раздел)** — логическая группировка для контроля доступа (может ссылаться на несколько Папок или фильтровать по атрибутам)

#### Б. Отсутствие иерархии Разделов

**Проблема:** Плоская структура Разделов не позволяет организовать вложенность. Например, нельзя сделать «Финансы → Бухгалтерия → Налоги» с наследованием прав от родителя к потомку.

**Риск:** При росте числа Разделов (50+) Админ теряет контроль над структурой. Пользователь получает «винегрет» из несвязанных Разделов.

**Рекомендация:** Добавить опциональную иерархию (дерево) с наследованием прав. Родительский Раздел может задавать базовые права, дочерние — расширять или сужать.

#### В. Конфликт Ролей: нет чёткого правила разрешения

**Проблема:** В концепции не определено, что происходит при конфликте:
- Роль А даёт доступ к Типу документа «Счёт» как «редактор»
- Роль Б запрещает доступ к Типу документа «Счёт»
- Что в итоге?

**Риск:** Неопределённое поведение, которое будет интерпретировано разработчиками по-разному в разных местах системы.

**Рекомендация:** Явно определить стратегию разрешения конфликтов:
1. **Запрет имеет приоритет** (наиболее безопасная стратегия, используется в большинстве корпоративных систем)
2. **Разрешение имеет приоритет** (менее безопасная, но более гибкая)
3. **Наиболее специфичное правило побеждает** (используется в AWS IAM)

Рекомендую стратегию №1 как наиболее предсказуемую.

#### Г. Теги: не определена модель управления

**Проблема:** В концепции теги упоминаются, но не определено:
1. **Кто присваивает теги пользователю?** Админ? Сам пользователь? Автоматика по событию?
2. **Кто присваивает теги документу?** Автор документа? Админ? Автоматика?
3. **Как разрешаются конфликты?** Если у пользователя есть тег из `or_tags`, но документ в `no_tags`?
4. **Есть ли наследование тегов?** Например, от должности, отдела, проекта.

**Риск:** Без чёткой модели управления теги быстро превратятся в хаос: каждый Админ будет присваивать их по-своему, пользователи не будут понимать, почему у них есть или нет доступа.

**Рекомендация:** Определить явную модель:
- Теги **пользователю** присваивает только Админ Организации (или Суперадмин)
- Теги **документу** присваивает Автор документа (или Админ)
- Конфликт: `no_tags` имеет приоритет над `and_tags`, `and_tags` — над `or_tags`
- Наследование тегов: от Организации → Раздела → Документа

#### Д. Теги: проблема производительности

**Проблема:** Если каждый документ содержит теги, и каждый запрос к документу должен проверять пересечение тегов пользователя и документа, это может стать узким местом.

**Риск:** При 10 000 документов и 1 000 пользователей, каждый запрос к списку документов может потребовать выполнения сложного фильтра по тегам. Это может замедлить систему до неприемлемого уровня.

**Рекомендация:**
1. **Денормализация**: хранить «итоговый набор тегов пользователя» в сессии / кэше, не пересчитывать на каждый запрос
2. **Индексация**: создать индексы на поля тегов в БД (GIN для JSONB / ARRAY)
3. **Предвычисление**: при изменении тегов пользователя или документа пересчитывать материализованное представление «доступные документы»

#### Е. Отсутствие временного измерения

**Проблема:** В концепции нет понятия «доступ на период»:
- Замещение на время отпуска
- Временный доступ к проекту
- Отзыв доступа по истечении срока

**Рекомендация:** Добавить опциональные поля `valid_from` и `valid_until` в связь Пользователь ↔ Роль.

#### Ж. Отсутствие аудита

**Проблема:** Нет механизма логирования:
- Кто предоставил доступ
- Когда был предоставлен доступ
- К каким документам был получен доступ
- Когда был отозван доступ

**Риск:** Невозможность расследования инцидентов, несоответствие требованиям регуляторов (152-ФЗ, ФЗ-187, отраслевые стандарты).

**Рекомендация:** Добавить таблицу `access_audit_log` с полями: `timestamp`, `user_id`, `role_id`, `doctype`, `section_id`, `action` (GRANT / REVOKE / ACCESS), `details`.

## 3. Предложения по улучшению

### 3.1. Разделение Папки и Пространства доступа

```
┌─────────────────────────────────────────────────────────┐
│  Папка (Folder) — физическая организация                │
│  ├── Иерархия (дерево)                                  │
│  ├── Не влияет на доступ                                │
│  └── Пользователь видит папки, к которым есть доступ    │
│                                                         │
│  Пространство доступа (AccessSpace / Раздел)            │
│  ├── Логическая группировка                             │
│  ├── Может ссылаться на несколько Папок                 │
│  ├── Может фильтровать по атрибутам (тип, тег, дата)   │
│  └── Привязывается к Роли                               │
└─────────────────────────────────────────────────────────┘
```

Это позволяет:
- Перемещать документы между Папками без изменения прав
- Создавать виртуальные Пространства доступа на основе фильтров
- Организовывать иерархию Папок независимо от прав

### 3.2. Явное разрешение конфликтов

Добавить в документацию и в код явное правило:

```
1. Если хотя бы одна Роль запрещает доступ (через no_tags или явное отсутствие разрешения) → доступ ЗАПРЕЩЁН
2. Если все Роли разрешают доступ, но с разными уровнями → применяется МАКСИМАЛЬНЫЙ уровень
3. Если Роли дают доступ к разным Разделам → область доступа является ОБЪЕДИНЕНИЕМ
```

### 3.3. Управление тегами: явная модель

| Кто | Что присваивает | Где | Когда |
|-----|-----------------|-----|-------|
| Админ Организации | Теги Пользователю | `UserModel.tags` или отдельная таблица | Вручную при настройке пользователя |
| Автор документа | Теги Документу | Поле документа | При создании / редактировании документа |
| Автоматика (событие) | Теги Документу | Триггер / хук | При наступлении события (смена статуса, региона и т.д.) |
| Система | Теги Разделу | `SectionModel.default_tags` | При создании Раздела |

**Приоритет при конфликте:**
```
Раздел (разрешение) → Роль (разрешение) → Пользователь (разрешение)
Раздел (запрет) → Роль (запрет) → Пользователь (запрет)

Итог: если на любом уровне есть запрет → доступ запрещён
```

### 3.4. Временные ограничения

Добавить в связь Пользователь ↔ Роль:
```python
class UserRoleLink(Base):
    user_id: uuid.UUID
    role_id: uuid.UUID
    valid_from: datetime | None  # Если не указано — бессрочно
    valid_until: datetime | None  # Если не указано — бессрочно
    granted_by: uuid.UUID  # Кто предоставил доступ
```

### 3.5. Аудит доступа

```python
class AccessAuditLog(Base):
    id: uuid.UUID
    timestamp: datetime
    tenant_id: uuid.UUID
    user_id: uuid.UUID
    role_id: uuid.UUID | None
    section_id: uuid.UUID | None
    doctype: str | None
    document_id: uuid.UUID | None
    action: AccessAction  # GRANT | REVOKE | ACCESS | CREATE | UPDATE | DELETE
    details: dict | None  # Дополнительные данные (какие теги, какие уровни)
```
